# Дизайн: усиление поиска систем покрытий (фасет химстойкости + опечаткоустойчивый поиск веществ + выравнивание архитектуры)

Дата: 2026-10-25. Статус: на утверждение.

## Намерение и зачем

Это **подготовка** к будущей фиче «подбор систем покрытий по письму» (`docs/plans`-черновик
`podbor-po-pismu-plan.md`, пользовательский). В той фиче инженер пересылает письмо заказчика,
LLM извлекает параметры и прогоняет их через поиск систем. Сам LLM-адаптер/IMAP/распознавание —
**следующая фаза, здесь не делаем**.

Ключевая мысль, которая задаёт эту работу: пользователю нужно **решение = система покрытий**,
а не отдельное покрытие. Но сегодня поиск систем заметно беднее поиска покрытий. Разбор показал
три асимметрии в пользу покрытий:

1. индекс покрытия включает **названия веществ, к которым покрытие стойко** (вес D, через
   `chemical_resistance_suitable_substance_names`); у системы такого нет;
2. у покрытий есть **fuzzy-fallback** (pg_trgm, опечатки), у систем нет;
3. поиск веществ (`SubstanceRepository::findByFilter`) — чистый **ILIKE-подстрока**, опечаток не ловит.

Эта работа закрывает (1) и (3) на стороне систем так, чтобы движок потом **переиспользовала фаза
письма** (программный вызов того же поиска), а пользователь уже сейчас искал системы по стойкости
к веществу.

## Решения, принятые при обсуждении (источник истины — они)

- **Мост «через покрытия» = только химстойкость.** Свободный текст по описаниям/тегам покрытий через
  мост НЕ тянем (обсуждали, отвергли). Строка поиска остаётся текстовым поиском систем.
- **Химстойкость — структурный ФАСЕТ, не строка.** Ввод — мультивыбор веществ (typeahead), не сырой текст.
- **Правило матча — «ВСЕ слои системы стойки к веществу».** Не верхний, не любой — все. Доменный выбор
  пользователя (я предупредил о разреженности данных у грунтов — принято осознанно).
- **«Стоек» = suitable-grade** через существующую `Grade::isSuitable()` / SQL `chemical_resistance_is_suitable_grade`
  (один источник истины с индексом покрытий).
- **Фильтр = `StringCollection` веществ + одна `?PositiveNumber` температура на весь набор.** T применяется
  в матче в v1 (задана → `max_temperature_celsius >= T`). `PositiveNumber` ⇒ T > 0.
- **Мультивыбор веществ = AND.** «Все слои стойки к этанолу И все слои стойки к воде» — верная
  семантика требований из письма.
- **Фасет сужает (AND), не расширяет.** Систему «стойкая к нефти по описанию, без данных» ловит строка
  (прямой FTS), не фасет. Аддитивный OR-союз отвергли как нестандартный.
- **Подложка остаётся существующим фасетом `cs.substrate`** (структурный, уже работает). Никакой подложки
  на покрытии, никакого парсинга описаний. Проблемы «для бетона строкой» не существует — substrate не идёт строкой.
- **Опечатки веществ лечим pg_trgm fuzzy** (как у покрытий). Защитный рельс: точное имя/CAS — авторезолв;
  fuzzy только предлагает кандидатов; в фазе письма человек подтверждает — химию молча не подменяем.

### Решения по объёму (подтверждены пользователем)

- **Строковый индекс системы оставляем как есть**: title + description + названия/производители покрытий
  слоёв + теги системы (`CoatingSystemSearchCacheRepository::buildFullTextSearchDocument`). Не режем до title+description.
- **Архитектуру поиска систем выравниваем заодно** (вариант «a» из обсуждения): фасет всё равно вшивается
  в `CoatingSystemFinder`; тащить фичу на двух движках с дублирующим suggest-ILIKE — закладывать долг.

## Goals

1. Новый фасет «стойкость к веществу(ам)» на поиске систем: `StringCollection` веществ + `?PositiveNumber`
   температура в `CoatingSystemsFilter`, матч «все слои стойки», AND между веществами, suitable-grade,
   T применяется когда задана.
2. Опечаткоустойчивый поиск веществ (`SubstanceRepository::findByFilter`): pg_trgm fuzzy + индекс.
   Служит и typeahead на странице, и будущему резолву в письме.
3. Выравнивание архитектуры поиска систем под эталон покрытий: единая точка `findByFilter`, убрать
   дублирующий suggest-ILIKE, унифицировать параметр `search`.
4. UI фасета на странице систем: мультивыбор веществ общим typeahead-компонентом, чипы в chip-row,
   состояние в URL, работа без JS.

## Non-goals / anti-goals

- **НЕ** LLM/IMAP/адаптер/распознавание письма — следующая фаза.
- **НЕ** температура в фасете химстойкости (v1).
- **НЕ** объединение страниц «покрытия» и «системы» в одну — отдельная задача, фиче не нужна.
- **НЕ** свободный текст по описаниям/тегам покрытий через мост.
- **НЕ** аддитивный OR-союз — фасет сужает.
- **НЕ** подложка на покрытии / «первый слой поддерживает» — substrate уже на системе.
- **Провал**, если: поиск систем стал у́же, чем был; строка перестала ловить то, что ловила; фасет
  отдаёт систему, у которой НЕ все слои стойки; добавление фасета сломало существующие фасеты/пагинацию/сортировку.

## Ограничения (правила проекта)

- Инвариант «что система выдерживает» — доменное свойство, выводимое из слоёв; но конкретная **техника
  поиска** (кросс-контекстный SQL в ChemicalResistance) — инфраструктура. Домен `Coatings` про таблицы
  `chemical_resistance_*` напрямую не знает; читаем их только в инфраструктуре поиска, как уже сделан
  фасет «есть документы» (лезет в `certificates_document` контекста Certificates).
- Один `findByFilter` на поиск/листинг; не плодить `suggest()/findByX()`. Лёгкий `*SuggestDTO` vs тяжёлый DTO —
  различие только в весе, путь один.
- Выбор сущности на фронте — общий `typeahead`-компонент, не самопал, не легаси `async-typeahead`.
- Состояние фильтра — в URL; форма работает без JS; чипы гидрируются by-ids.
- Инварианты полей фильтра — в узких VO; `CoatingSystemsFilter` — bag-of-fields.
- `id`-списки — `StringCollection`.
- Бэк — источник истины; фронт только показывает.

## Как это устроено (решённое)

### 1. Фасет химстойкости в домене фильтра

Фильтр несёт **список UUID веществ + одну опциональную температуру на весь набор** — из готовых кирпичей
проекта (`StringCollection` для id-шек, `?PositiveNumber` для T), не самодельный VO-коллекция:

```php
// в CoatingSystemsFilter:
public StringCollection $substanceIds = new StringCollection(),
public ?PositiveNumber $substanceTemperature = null,   // одна T на весь набор; PositiveNumber ⇒ T > 0
```

Семантика — «система, у которой ВСЕ слои стойки к КАЖДОМУ из веществ; при заданной T — с запасом по
температуре» (AND между веществами, одна T применяется ко всем). Резолв слова → UUID происходит ДО фильтра
(пикер на странице / резолвер в фазе письма); в фильтр приходят чистые UUID. Сам матч — в инфраструктуре поиска.

### 2. Матч в поиске (инфраструктура)

`App\Coatings\Infrastructure\Search\CoatingSystemFinder::find` — добавляется `applySubstanceResistance`.
Для каждого вещества (AND, повтор условия) — слой без suitable-оценки по этому веществу не должен
существовать, и у системы должен быть хотя бы один слой (иначе `NOT EXISTS` над пустым множеством даёт
ложный vacuous-match). Температура (одна на набор) добавляет условие `>= T` в ту же suitable-проверку,
когда задана:

```sql
AND EXISTS (SELECT 1 FROM coating_system_layer gl WHERE gl.system_id = cs.id)   -- guard: система непустая
AND NOT EXISTS (
    SELECT 1 FROM coating_system_layer csl
    WHERE csl.system_id = cs.id
      AND NOT EXISTS (
          SELECT 1 FROM chemical_resistance_assessment a
          WHERE a.coating_id = csl.coating_id
            AND a.substance_id = :subst_i
            AND chemical_resistance_is_suitable_grade(a.grade)
            AND (:temp IS NULL OR a.max_temperature_celsius >= :temp)   -- T одна на весь набор, применяется если задана
      )
)
```

- **Живой запрос, без проекции.** Изменение оценок у покрытия сразу влияет на выдачу — ничего
  перестраивать не надо (в отличие от tsvector-кэша). Осознанный выбор: корректность важнее скорости;
  если будет медленно — оптимизируем индексом/проекцией, но не в v1.
- Данные химстойкости — `chemical_resistance_assessment(coating_id, substance_id, grade, max_temperature_celsius)`;
  «стоек» = `chemical_resistance_is_suitable_grade(grade)`.
- **Температура применяется в матче v1** (решено): задана T → слой годится только при `max_temperature_celsius >= T`.
  `PositiveNumber` гарантирует T > 0.

### 3. Опечаткоустойчивый поиск веществ

**Фактическая поправка после builder-check.** Поиск веществ в коде расходится на ТРИ пути, и typeahead
идёт НЕ через `findByFilter`:

- `SubstanceAutocompleteQueryHandler` (свой DBAL-ILIKE) — это и есть **typeahead-endpoint**, его ест
  `substance-multiselect`/picker;
- `SubstanceRepository::findByFilter` (ILIKE по `canonical_name`/`cas`/`aliases`) — только **страница-список** веществ;
- `MatchSubstancesForSearchQueryHandler` (FTS-мост) — третий путь.

Заголовочная выгода «этоно… → этанол в пикере» достигается, только если fuzzy попадёт в **autocomplete-путь**.
Приём fuzzy — тот же, что в `CoatingFinder::fuzzyTitle`:

- основной путь — ILIKE (точное/подстрока), высший приоритет;
- нет точного/подстрочного → триграммный fallback: `similarity`/`WORD_SIMILARITY` по `canonical_name`
  (и, возможно, aliases) выше порога, `ORDER BY sim DESC`;
- GIN-trgm индекс на `canonical_name` (миграция). pg_trgm в проекте уже есть (его гоняют покрытия).

Куда именно кладём fuzzy и консолидируем ли autocomplete в `findByFilter` — **развилка Q1 ниже (решение
пользователя)**: fuzzy обязан быть в autocomplete-пути; консолидация трёх путей в один `findByFilter` —
вопрос объёма/риска.

**Защитный рельс** (действует в фазе письма, здесь только фундамент): точное имя/CAS — авторезолв; fuzzy
только кандидаты; авто-подмену вещества не делаем.

### 4. Выравнивание архитектуры поиска систем

- Ввести `CoatingSystemRepository::findByFilter(CoatingSystemsFilter): PaginationResult|SearchResult` как
  единую точку; `CoatingSystemFinder` прячется за ней (как у покрытий `CoatingRepository::findByFilter` →
  `CoatingFinder`).
- Убрать `SearchCoatingSystemsForSuggestQueryHandler` с собственным `ILIKE`-путём; suggest систем ходит
  через тот же `findByFilter`, отличаясь только лёгким `CoatingSystemSuggestDTO` (как у покрытий
  `CoatingSuggestDTO` vs `CoatingDTO`).
- Унифицировать параметр свободного текста: `search` (сейчас у систем `q`). Обновить request-mapper и шаблон.

### 5. UI фасета на странице систем

- Страница `cabinet/coating/coating_system/list.html.twig`. Фасет «Стойкость к веществу» — мультивыбор
  общим `typeahead`-компонентом по справочнику веществ (тот же endpoint/справочник, что страница
  «по веществу»), `hidden-name="substanceIds[]"`, выбранные — чипы в chip-row как активные фасеты, × снимает.
- Состояние в URL (`substanceIds[]`), гидрация чипов by-ids (имена веществ подтягиваются по id, без
  резолва на сервере в контроллере).
- Без JS — обычный GET с `substanceIds[]` отрабатывает серверной стороной.

## Что оставлено билдеру

- Точный порог fuzzy веществ и надо ли включать `aliases` в триграммный индекс/поиск.
- Точное имя лёгкого `CoatingSystemSuggestDTO` и его поля.
- Нужен ли индекс на `chemical_resistance_assessment(coating_id, substance_id, grade)` для скорости
  `all-layers`-EXISTS (замерить; скорее да).
- Конкретный endpoint by-ids для гидрации чипов веществ (переиспользовать существующий у ChemicalResistance,
  если есть; иначе добавить тонкий).
- Точка переиспользования поиска будущей фазой письма — это `CoatingSystemRepository::findByFilter`;
  отдельного публичного фасада сейчас не вводим (чужой контекст позовёт Application-query поверх него, как
  предписывают правила границ).

## Уточнения после builder-check

### Q1 (решено) — один fuzzy-метод поиска веществ, безопасная консолидация

Нужен ОДИН метод «нечёткое слово → список веществ-кандидатов», общий для пикера на странице и для
будущего резолвера письма. Решение:

- fuzzy (триграмма) живёт в `SubstanceRepository::findByFilter` — это и есть единый метод;
- autocomplete-endpoint (`SubstanceAutocompleteQueryHandler`) **делегирует в него**, СОХРАНЯЯ свой текущий
  JSON-ответ — поэтому страница «по веществу» (`substance-multiselect`) не ломается;
- список-страница веществ тоже идёт через него.

Так правило «один findByFilter» соблюдено, а регресса соседней страницы нет (контракт endpoint сохранён).

### Микро-решение — температура в матче v1 (решено)

Применяем в v1. Поле — `StringCollection $substanceIds` + одна `?PositiveNumber $substanceTemperature` (на весь
набор). Задана T → слой годится только при `max_temperature_celsius >= T`; не задана — условие по T отключено.

### Решения автора (вето при чтении) — Q2–Q5

- **Q2. Компонент фасета веществ — копируем ближайший аналог на ЭТОЙ же странице:** мультивыбор-фасеты
  «Покрытия в составе»/«Теги» сделаны контроллером `coating-tags` (чипы, клиентская гидрация by-ids через
  `resolve-url`). Фасет веществ строим так же + добавляем тонкий **substance by-ids** endpoint для гидрации
  чипов. НЕ используем generic single-select `typeahead` и НЕ копируем серверные чипы `substance-multiselect`
  (он для страницы «по веществу»). Правка спеки: исходная формулировка «общий typeahead, чипы by-ids без
  сервера» заменяется на «образец — `coating-tags` на этой странице».
- **Q3. Унифицированный строковый путь НЕ должен сузиться.** Сейчас suggest = `FTS OR title ILIKE`, список =
  FTS-only. При консолидации единый путь **повышаем**: FTS + ILIKE-infix + триграммный fallback (как у
  покрытий), чтобы suggest не потерял infix-хиты, а список заодно стал шире (это цель, не регресс). Опираемся
  на гарантию sync-шины, что у каждой системы есть строка `coating_system_search` (INNER-join безопасен).
- **Q4. Контракт `CoatingSystemRepository::findByFilter` — возвращает гидрированный `PaginationResult`
  сущностей** (как у покрытий): внутри прячет Finder(ids)+`findByIds`. Обогащение (compliance-кэш,
  сертификаты-шлюз, DTO-трансформер) **остаётся в Application-хендлере** поверх сущностей. Это и точка
  переиспользования для фазы письма.
- **Q5. `q` → `search`: без ломки закладок.** Mapper основным читает `search`, но принимает `q` как
  fallback (эмитит `search`). Старые `?q=…` ссылки продолжают работать.

## Тесты

- **Finder (functional, реальная БД):** система, где все слои стойки → в выдаче; система, где у одного слоя
  нет оценки → НЕ в выдаче; где у слоя оценка несуитабельного grade → НЕ в выдаче; два вещества (AND);
  пустая система не даёт vacuous-match; фасет не ломает существующие фасеты/сортировку/пагинацию.
- **Substance fuzzy (functional):** «этонол» → «этанол» выше порога; точное/подстрока работает как раньше;
  отсутствие ложных хитов уровня «мастик»→«Литапрайм».
- **Консолидация:** suggest систем даёт ту же широту, что list (один путь); лёгкий DTO отдаёт ожидаемый shape.
- **Mapper round-trip:** `substanceIds` форма↔DTO↔URL.

## Пересечения контекстов

- `Coatings` (поиск) читает `chemical_resistance_assessment` и зовёт `chemical_resistance_is_suitable_grade`
  только в SQL инфраструктуры поиска — прецедент: фасет «есть документы» читает `certificates_document`.
- Фаза письма (следующая, не здесь) позовёт поиск систем через Application-query контекста `Coatings`,
  не напрямую в БД.
