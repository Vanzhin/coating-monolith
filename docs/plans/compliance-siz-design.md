# Дизайн: учёт обязанностей по охране труда (Compliance) + профиль сотрудника (Personnel). Первый полный тип — выдача СИЗ

> Дизайн-спека (архитектура и решения). Планы реализации по деплоям — отдельные файлы `docs/plans/compliance-siz-N-*.md`, собираются через writing-plans после утверждения этой спеки.

## 1. Цель

Компания обязана обеспечивать/контролировать сотрудников по нормативам: выдавать СИЗ (раз в год / раз в N лет / до износа), проводить инструктажи (периодические и **однократные** — напр. на рабочем месте при поступлении), вести журналы. Нужен инструмент, который:

- хранит **требования по должности** — что положено/что нужно пройти (список обязанностей, у каждой свой тип и своя cadence);
- ведёт **учёт по человеку** (наследует требования его должности + индивидуальные отклонения);
- фиксирует **факты** (выдачи/возвраты, прохождение инструктажа) с датами и опц. сканом;
- **трекает статус** каждой обязанности и сводит его в **светофор по человеку**;
- **алертит ответственного**, когда подходит срок или обязанность просрочена/не выполнена;
- **генерирует документ** (для СИЗ — Excel-карточка учёта).

**Строим generic-ядро обязанностей + дашборд сразу.** СИЗ — **первый полный тип** (кол-во, %износа, размер, Excel-карточка). Инструктажи/журналы — **лёгкие обязанности** (наименование + cadence + дата выполнения + опц. файл): достаточно для светофора и отметки «выполнено», без собственной rich-формы/документа (её сделаем, когда возьмём тип целиком). Это не schemaless-блок-система — поля фиксированы и типизированы.

## 2. Границы

**В объёме:**
- Домен `Personnel`: `Profile` (0..1 на `User`), `Position` (должность, quick-create), `Department` (отдел — иерархический, привязан к компании, начальник на узле).
- Домен `Compliance` (generic-ядро): требования по должности (обязанности разных типов и cadence), учёт по человеку + журнал фактов, трекинг статуса, **дашборд-светофор** (по людям и отделам), генерация Excel-карточки СИЗ.
- СИЗ — полный тип; инструктажи/журналы — лёгкие обязанности.
- Двухуровневая ответственность + алерты через общий `symfony/scheduler`.

**Вне объёма (осознанно):**
- Schemaless блок-система полей (Reports `BlockDefinition`/`Field`) — не используем.
- Rich-формы/документы для инструктажей (ТБ/высота как полноценные типы со своими полями и бланками) — позже; в v1 они лёгкие.
- Массовый импорт сотрудников — нет, админ заводит `User`+`Profile` вручную.
- UI орг-карты компании — не строим, но данные `Department` (дерево+компания) готовим под неё.
- Вынос `Counterparty` в отдельный домен «Организация» — на потом.
- Скоуп дашборда под ответственного (начальник видит только своих) — в v1 админ видит всех; скоуп — позже.
- Личный внешний канал сотрудника (email/telegram) — точка расширения.

## 3. Ключевые решения (зафиксированы с заказчиком)

1. **`Profile` — отдельный домен, не поля на `User`.** `User` — якорь, `Profile` (0..1) ссылается по `userUlid`. Большинство — учётки-оболочки без логина, заводит админ вручную.
2. **Generic-ядро обязанностей + типы-плагины.** Ядро (требования по должности, cadence, учёт, журнал, трекинг статуса, дашборд, планировщик, пайплайн документа) — не зависит от типа. От типа зависит: спец-поля (СИЗ: кол-во/%износа/размер), шаблон документа, применимые виды cadence, «полный/лёгкий». Контракт типа проектируем по СИЗ (единственный полный пример); при втором полном типе шов уточним.
3. **`Department` — иерархический справочник, привязан к компании (`Counterparty`).** Отдел содержит подотделы (self-parent дерево), на узле — начальник (`headUserUlid`). Данные под будущую орг-карту. Организация-работодатель = существующий `Counterparty` (ИНН+quick-create), живёт в Reports; вынос в отдельный домен — потом.
4. **Требования по должности (редактируемый набор) + персональные добавки/исключения.** Должность → **редактируемый админом** список обязанностей {наименование, тип, cadence, кол-во?, основание?} — обязательный набор должности (СИЗ, ТБ, …). Учёт человека наследует набор его должности **снапшотом** + **персональные добавки** (напр. инструктаж по высоте на конкретного человека) и исключения. Всё, что попало в учёт человека, трекается одинаково: **различия «обязательно/опционально» нет** (решение заказчика — «без разницы, обязательно или нет; если добавлено, то трекается»). «Опционально» = опционально ДОБАВИТЬ (не у всех), а не опционально выполнять; не нужна позиция конкретному человеку — админ её исключает из его учёта.
5. **Cadence включает «однократно».** Виды: `однократно` / `год` / `N лет` / `N месяцев` / `до износа (≤N мес)` / `по документам изготовителя`. Однократная выполнена → закрыта навсегда; периодическая → считает `nextDueAt`.
6. **Статус-светофор** (см. §4.4): требуется-и-не-выполнено → красный; периодическое просрочено → красный; ≤14 дней до срока → жёлтый; иначе зелёный; однократное выполнено → зелёный. **Статус человека = худший по всем его требуемым обязанностям** (с учётом фильтра по типу).
7. **Дашборд** — карточки по людям (имя + агрегатный цвет), группировка **по пользователю и по отделу** (дерево), фильтр по типу («только СИЗ»), обычные фасеты+чипы (URL-state). **Админ видит всех.** Дизайн карточки прорабатываем отдельно.
8. **Ответственный — двухуровневый.** Начальник узла отдела (с обходом дерева вверх) = дефолт по всем формам; переопределение по форме (СИЗ→Иванов) выигрывает. Резолв: `ответственный_по_форме ?? начальник_отдела(обход вверх)`.
9. **Оповещение на человека** через `SendNotificationCommand(responsibleUlid)` + копия в inbox сотрудника (у трекаемого всегда есть `User`).
10. **Учёт всегда редактируем админом** — жизненного цикла/edit-lock нет; журнал правится.
11. **Документ СИЗ — Excel** (PhpSpreadsheet). Движок умеет и Word — для будущих типов.
12. **Планировщик — `symfony/scheduler`, общий backbone на всё приложение** (расписание в коде, гоняет существующий Messenger-воркер).
13. **Отдельная секция/вкладка**, не под Reports.

## 4. Доменная модель

### 4.1 `Personnel` (Персонал)

**`Profile`** (агрегат): `Uuid $id`; `string $userUlid` (обязателен; один профиль на юзера — доменная спека уникальности); `FullName` VO `{lastName, firstName, ?middleName}`; `string $positionId` (снапшот `Reference {id,title}` на `Position`); `string $organizationId` (снапшот на `Counterparty`); `string $departmentId` (снапшот на узел `Department`; инвариант: компания отдела = `organizationId`); `?string $personnelNumber`; `?\DateTimeImmutable $hiredAt`; `Sizes` VO (одежда/обувь/головной убор/противогаз/респиратор/перчатки/рост/пол — все опц.); `createdAt/updatedAt`, `int $version`.

> «Структурное подразделение» отдельным текстовым полем не храним — его роль играет узел `Department` (путь компания→отдел→подотдел).

**`Position`** (агрегат-справочник, зеркало `Counterparty` без ИНН): `Uuid $id`, `string $title` (уникален), quick-create. Per-action контроллеры `Add/Update/Delete/List/Suggest/QuickCreate/ByIds` (+ `async_typeahead_controller.js`).

**`Department`** (агрегат-справочник, иерархический): `Uuid $id`, `string $title`, `string $companyId` (`Counterparty`), `?string $parentId` (дерево; null=корень), `?string $headUserUlid` (начальник). Инварианты: parent той же компании, без циклов. Управляемый CRUD с деревом; орг-карта — потом.

### 4.2 `Compliance` — требования и учёт

**`ObligationType` — тип обязанности как стратегия-плагин (интерфейс + tagged-реестр).** Ровно паттерн `BlockDefinition`+`BlockRegistry` из Reports, но для типов. Интерфейс объявляет: `key()`/`title()`, применимые виды cadence, есть ли количество, свои доп-поля + их валидацию, проекцию в документ (если есть). Конкретный тип = класс, реализующий интерфейс, с DI-тегом → `ObligationTypeRegistry` (`!tagged_iterator`) собирает их. v1: `Ppe` (СИЗ — кол-во/%износа/размер + Excel-документ) + лёгкий тип(ы) под инструктажи/журналы.

**Расширяемость «подключить задачу» (цель заказчика).** Новый трекаемый тип = (1) класс, реализующий `ObligationType`; (2) DI-тег; (3) всё — тип появляется в редакторе нормы, трекается/агрегируется/алертится единообразно, попадает в фильтр дашборда. **Ядро не трогаем** (трекинг, дашборд, планировщик, журнал, CRUD). Миграция нужна лишь если у типа свои индексируемые колонки; лёгкий тип живёт на общей плоской таблице позиций + `attributes` (JSONB) — без миграции.

> **Интерфейс — на ТИП (стратегия), не на item.** Позиция (`ObligationItem`) остаётся ЕДИНОЙ трекаемой сущностью (общие колонки + маленький тип-специфичный `attributes` JSONB). Полиморфную сущность-item НЕ делаем: ~90% позиции общее (cadence/журнал/nextDue/status/трекинг), тип-специфичного мало — полиморфизм дал бы дублирование общего трекинга и мешал бы плоским queryable-колонкам для дашборда/планировщика. Контракт `ObligationType` проектируем по СИЗ+лёгкому инструктажу; при реально ином типе интерфейс может обрасти методом, но ядро стабильно. Таксономия лёгких типов — §10.

**Единая форма — требование = коллекция позиций (`iterable`), без «моно vs сборник», без флага `isItemized`.** У каждого требования (по типу) есть коллекция позиций. **Моно** (инструктаж) = коллекция из **1** позиции; **СИЗ** = коллекция из **N** позиций (костюм, ботинки, перчатки). Обработка и редактирование **единообразны**: итерируем позиции требования; статус требования = худший по его позициям; статус человека = худший по требованиям. Тип определяет, какие объекты кладём в коллекцию (СИЗ-позиции vs один инструктаж), но контейнер и итерация — общие. Никаких веток «СИЗ особый».

Позиция — `ObligationItem` (у человека) / `RequirementItem` (в норме) = {наименование, cadence, кол-во?, journal, срок, статус, origin/normQuantity}. **Кол-во** — опциональный атрибут позиции (есть у СИЗ, нет у инструктажа). Пер-персон правки (добавить позицию, убрать, изменить кол-во с floor ≥ нормы) — единообразны для позиции любого типа.

**Хранение (чтобы дашборд/планировщик были дешёвыми):** трекаем и храним именно **позиции** — плоская таблица `ObligationItem` с `person`/`type`/`status`/`next_due` (индексы). «Требование = коллекция позиций данного типа» — группировка над плоскими позициями (по `type`). Снаружи единая iterable-модель, внутри — queryable плоские позиции. Группировка/фильтр/документ/ответственный — по `type`.

> Терминология (унифицируется при планировании Д2/Д3): в разделах ниже `RequirementLine` = `RequirementItem` (позиция нормы), `TrackedObligation` = `ObligationItem` (позиция человека) — одно и то же, разные рабочие имена. Финальные имена зафиксируем в планах Д2/Д3.

**`Cadence`** (VO) — вид + значение (§3.5). `nextDueFrom(\DateTimeImmutable $base): ?\DateTimeImmutable`: периодические → дата; `однократно`/`по документам изготовителя` → null (срок не вычисляется автоматически). Инварианты (N>0) в конструкторе → `AppException`.

**`PositionRequirements`** (агрегат) — **редактируемый админом** набор требований должности: `positionId` + `RequirementLine[]`. `RequirementLine` (VO): `string $label`, `ComplianceType $type`, `Cadence $cadence`, `?string $basis` (пункт норм/основание), `?Quantity $quantity` (для СИЗ; кол-во+ед.изм), + type-extras. Админ редактирует табличным редактором (паттерн AJAX-строк как у слоёв системы / list-rows). Это обязательный набор для должности (СИЗ, ТБ, …). «Норма СИЗ» = подмножество строк с `type=Ppe`. **Флага «обязательно/опционально» на строке НЕТ** — всё, что в наборе, обязательно; «опциональность» = персональные добавки/исключения на уровне `PersonCompliance`.

**`PersonCompliance`** (агрегат, **один на человека**) — учёт обязанностей сотрудника:
- `string $subjectUserUlid`.
- `TrackedObligation[]` — что отслеживаем. Наследуется **снапшотом** из `PositionRequirements` его должности при создании/пересинхронизации (заморозка — правки требований не переписывают учёт задним числом; ресинк — явным действием), + **персональные правки**: добавить позицию (напр. инструктаж по высоте; для СИЗ — солнцезащитные очки), убрать ненужную, **изменить кол-во** конкретной позиции.
- `FulfillmentRecord[]` — журнал фактов.
- **Всегда редактируем админом**, edit-lock нет.
- **Пер-персон гибкость СИЗ (сборник).** По умолчанию у человека — снапшот СИЗ-позиций нормы его должности. Админ на карточке может:
  - **увеличить кол-во** Norm-позиции — но **не ниже нормы** (норма = гарантированный минимум: сапоги 2 пары/год → можно 3, нельзя 1). Инвариант в домене: для `origin=Norm` `quantity >= normQuantity`, иначе `AppException('Нельзя выдать меньше нормы должности (N).')`.
  - **добавить свою позицию** (`origin=Personal`, напр. очки) — любое положительное кол-во.
  - убрать позицию — **см. открытый вопрос §10** (норма-минимум: Norm-позицию убрать нельзя, только Personal; уточняется).
  Чтобы ресинк с нормой не затирал личное — у `TrackedObligation` есть `origin` (`Norm`/`Personal`), `?Quantity $normQuantity` (базлайн нормы, для floor у Norm) и `quantityOverridden: bool`; ресинк обновляет Norm-позиции без override, сохраняя Personal и переопределённые поля.

> Имя `PersonCompliance` (не «карточка») — чтобы не путать с UI-«карточкой пользователя» (плитка дашборда) и с генерируемым документом «Личная карточка учёта выдачи СИЗ» (Excel-проекция СИЗ-подмножества).

**`TrackedObligation`** (сущность внутри `PersonCompliance`): `string $label`, `ComplianceType $type`, `Cadence $cadence`, `ObligationOrigin $origin` (`Norm`/`Personal`), `?Quantity $quantity`, `?Quantity $normQuantity` (базлайн нормы для floor у Norm-позиций; null у Personal), `bool $quantityOverridden`, `?\DateTimeImmutable $lastFulfilledAt`, **вычисляемый `?\DateTimeImmutable $nextDueAt`**, **`ComplianceStatus $status`** (тоже персистится — см. §8). Пересчёт `nextDueAt`+`status` — в домене при добавлении/правке факта; изменение кол-ва проверяет floor (`quantity >= normQuantity` для Norm). `next_due_at`/`status` **индексируются** для дешёвого дашборда/планировщика.

**`FulfillmentRecord`** (сущность журнала): `\DateTimeImmutable $fulfilledAt` (выдано/пройдено), `?Quantity $quantity`, `?Percent $wearPercent` (СИЗ), `?string $note`, `?string $fileId` (скан, UUID `StoredFile`), опц. возврат (`returnedAt`,кол-во). Привязка к `TrackedObligation`. Правится/удаляется админом.

### 4.3 Ответственность

- `FormResponsible` (конфиг) — `ComplianceType → userUlid` (глобально на форму в v1).
- `ResponsibilityResolver` (Application-сервис `Compliance`): `resolve(subjectUserUlid, ComplianceType): ?userUlid` = `FormResponsible(type) ?? headOfDepartment(person)`. Начальник — **обходом дерева вверх** от узла человека до корня компании (первый непустой `headUserUlid`). Профиль/отдел/дерево — из `Personnel` через query-шину (`GetResponsibleHeadQuery(subjectUserUlid): ?userUlid`).

### 4.4 Статус-светофор (доменная логика)

`ComplianceStatus` enum: `Green` (ок), `Yellow` (подходит), `Red` (внимание). Порог жёлтого — 14 дней (константа, настраиваемая).

Статус `TrackedObligation` (`now`). Всё, что попало в учёт человека, требуется одинаково — различия «обязательно/опционально» нет (решение заказчика):
- **не выполнено ни разу** (`lastFulfilledAt == null`) → **Red** («необходимо выполнить/выдать»). Покрывает однократный инструктаж и «ещё не выдавали СИЗ».
- периодическое, выполнено: `nextDueAt < now` → **Red**; `nextDueAt <= now+14д` → **Yellow**; иначе **Green**.
- однократное, выполнено → **Green** (повтора нет).
- `по документам изготовителя`: срок ввели вручную на факте → как периодическое по этой дате; если факта нет → **Red**.

Не нужна позиция конкретному человеку — админ **исключает** её из его учёта (не трекается → не краснит), а не помечает «опциональной».

Статус **человека** = худший (`Red>Yellow>Green`) по его `TrackedObligation` в области фильтра (все типы / выбранный тип). Считается запросом по индексам `subject_user_ulid` + `status`/`next_due_at` — без загрузки агрегатов. Алерты (Д4) — по всем трекаемым обязанностям человека.

### 4.5 Что общее, что от типа

| Общее (ядро, пишем раз) | От типа |
|---|---|
| `PositionRequirements`/`RequirementLine`, редактор требований | Спец-поля строки (СИЗ: кол-во/размер) |
| `Cadence` + расчёт `nextDueAt`/статуса | Набор применимых видов cadence |
| `PersonCompliance` + снапшот-наследование + отклонения | Спец-поля записи (СИЗ: %износа), «полный/лёгкий» |
| `FulfillmentRecord` журнал (дата+файл) | — |
| Дашборд-светофор, группировки, фасеты | — |
| `ResponsibilityResolver`, планировщик-алерт | — |
| Пайплайн генерации документа | Шаблон Excel/Word (у лёгких типов документа нет) |

## 5. Дашборд (read-side)

- **Единица списка** — человек (`PersonCompliance`), плитка: ФИО + агрегатный цвет.
- **Группировка**: по пользователю (плоско) и **по отделу** (заголовки по дереву компании; узел можно сворачивать). Переключатель режима.
- **Фильтр по типу** — «только СИЗ» и т.п.: агрегатный цвет пересчитывается по подмножеству.
- **Фасеты+чипы** (URL-state, паттерн проекта): тип, отдел, должность, организация, статус-цвет, поиск по ФИО. Точный набор — уточним в плане Д4.
- **Доступ**: админ видит всех (скоуп под ответственного — позже).
- Запросы — по индексам (`subject_user_ulid`, `status`, `next_due_at`, `type`); группировка по отделу — join к снапшоту отдела/дереву. Дизайн плитки — отдельно.

## 6. Планировщик — `symfony/scheduler` (общий backbone)

В проекте нет крона (только supervisor гоняет `messenger:consume async`). Вводим `symfony/scheduler` **на всё приложение**: расписание в коде (`#[AsSchedule]` + `RecurringMessage::every('1 day', ...)`), любой контекст добавляет задачи в одном месте; гоняет существующий Messenger + один supervisor-consumer scheduler-транспорта (образец `messenger-worker.conf`). Compliance: `NotifyDueMessage` (ежедневно) → грузит `TrackedObligation` со `status IN (Red,Yellow)` (или `next_due_at <= now+порог`) → резолвит ответственного → `SendNotificationCommand` (+копия сотруднику). Дедуп: пометка «оповещён по item», сброс после факта. Проверить, что scheduler-воркер ставит системный принципал (как CLI `ConsoleAuthenticationSubscriber`); если нет — добавить эквивалент. Совместимость — проект уже на Symfony 8, см. [[project_php85_symfony8_upgrade]].

## 7. Авторизация и доступ

- Аутентификация — `security.yaml` (`/cabinet` → `IS_AUTHENTICATED`); `#[IsGranted]` не используем.
- Авторизация — `ComplianceAccessControl`/`PersonnelAccessControl` в Application. Модель cabinet: просмотр всем авторизованным, мутация — `ROLE_ADMIN` (см. `project_cabinet_access_model`), capability `canManage(): bool` через `AccessGuard::isManager()`.
- Учёт всегда редактируем админом (только гейт роли, доменного edit-lock нет).
- Файлы — `PpeCardFileAccessControl` (тег `app.file_access_control`) делегирует в `ComplianceAccessControl`; иначе `/cabinet/file/{uuid}` → 403 (deny-by-default).
- Отказ — `ForbiddenException` (403). Кнопки под `{% if canEdit %}` (UX).

## 8. Персистентность

- ORM XML на контекст (`src/Personnel/...`, `src/Compliance/...`), регистрация в `doctrine.yaml` (`orm.mappings` — блок на контекст, как `Reports`/`SharedFile`).
- VO как JSONB-колонки (`Sizes`, `FullName`, `Reference`-снапшоты, `Cadence`, `Quantity`) — DBAL-типы наследуют `AbstractJsonObjectType` (VO = `JsonSerializable`+`fromArray`), регистрируются в `doctrine.dbal.types`.
- **Дивергенция от Reports (осознанно):** трекинг — не документ-снапшот в одном jsonb, а **запрашиваемые** сущности. `TrackedObligation`/`FulfillmentRecord` — дочерние строки (реляционно); `next_due_at`, `status`, `type`, `subject_user_ulid` — колонки+индексы (дашборд/планировщик без сканов). `RequirementLine` — jsonb внутри `PositionRequirements`. `Department` — реляционно (self-ref parent, индекс companyId/parentId) для обхода дерева.
- Репозитории — `ServiceEntityRepository implements *RepositoryInterface`, алиас в `services.yaml`.
- Роуты — блок в `routes.yaml` на `src/{Personnel,Compliance}/Infrastructure/Controller`.
- Миграции — идемпотентные (`IF NOT EXISTS`), `src/Shared/Infrastructure/Database/Migrations/Version*.php`.

## 9. Потоки

1. **Оргструктура/справочники:** админ строит дерево `Department` компании + назначает начальников; создаёт `Position` (quick-create).
2. **Требования по должности:** админ редактирует список обязанностей должности (наименование, тип, cadence, кол-во/основание) — табличный редактор.
3. **Профиль:** админ создаёт `User` → `Profile` (ФИО, должность, организация, отдел-узел, размеры, таб.№, дата приёма).
4. **Учёт:** создаётся `PersonCompliance` → снапшот требований должности в `TrackedObligation[]` → индивидуальные отклонения.
5. **Факт:** админ фиксирует выдачу/прохождение (дата, для СИЗ — кол-во/%износа, опц. скан через stage→promote) → домен пересчитывает `nextDueAt`+`status`.
6. **Дашборд:** админ видит людей со светофором, группирует по отделу/пользователю, фильтрует по типу.
7. **Алерт:** `symfony/scheduler` (ежедневно) → подошедшие/просроченные/невыполненные → резолв ответственного → уведомление (+копия).
8. **Документ:** генерация Excel-карточки СИЗ — проектор собирает `RenderData` (идентичность из профиля + СИЗ-обязанности + журнал) → readiness → рендер → отдать файл.

## 10. Открытые вопросы

1. **Таксономия лёгких типов** (инструктажи/журналы): фиксированный code-enum `ComplianceType` (просто добавляем кейсы — рекомендую, «сначала встроенное») или админ-справочник типов. Решить в Д2. От этого зависит фильтр по типу на дашборде.
2. **Перечень отделов/структура компании** — стартовые данные из их файла (лист «Список»).
3. **`Quantity`/ед.изм** — enum единиц (шт./пара/мл/комплект…) или свободный текст. Уточнить в Д2.
4. **Фасеты дашборда** — финальный набор (§5). Уточнить в Д4.
5. **Принципал scheduler-воркера** — ставит ли системный (как CLI); если нет — добавить.
6. **Ресинк требований → учёт — РЕШЕНО (2026-09-29): сверка с АКТУАЛЬНОЙ нормой, без заморозки снимка.** Заказчик: норма изменилась (ботинки 1→2 пары/год) → сотрудник обязан догрузиться; проверка статуса сравнивает с ДЕЙСТВУЮЩИМИ требованиями его должности, не с копией на момент заведения. Значит **`PersonCompliance` НЕ хранит снимок нормы** — «требуемое» берётся ЖИВЬЁМ из `RequirementSet` текущей должности (Д2); учёт человека хранит только ФАКТЫ выдачи/прохождения (`FulfillmentRecord`) + персональные добавки/исключения/override кол-ва. Статус позиции = сравнение факта (что и когда выдано) с текущим требованием (кол-во+cadence): норма выросла → недостача → красный/«выдать ещё». Это пересматривает §4.2 (там был снимок) — учитывать при планировании Д3.
7. **Убирать ли Norm-позицию у человека.** Норма = гарантированный минимум (кол-во только вверх, `quantity >= normQuantity`). Открыто: можно ли вовсе исключить Norm-позицию у человека (=0<нормы), или Norm-позиции неудаляемы (только увеличение), а исключать/удалять можно лишь Personal-добавки. Предв. решение: Norm неудаляема, удаляется только Personal — **ждёт подтверждения заказчика**. Уточнить в Д3.
8. Вынос `Counterparty` в домен «Организация», скоуп дашборда под ответственного — отложено.
