# Деплой «периодическая позиция» (унификация инструктаж+расходник) — дизайн

**Дата:** 2026-10-20
**Контекст:** bounded context Compliance. Продолжает [compliance-journal-model-design.md](compliance-journal-model-design.md). Идёт ПОСЛЕ выноса проекции (read-модель `compliance_obligation_projection`, bucket на чтении, единый `ComplianceBucketResolver`) — всё в main. Отменяет ранее рассматривавшийся «Вариант B / тающий held» как неоправданное усложнение.

## 1. Цель и зачем

Сегодня позиция требования — это `ComplianceType::Material` (с `MaterialMode`: Inventoried/Consumable) либо `NonMaterial`. Расходник (ДСИЗ: крема/мыло) ошибочно сидит как «материальное с mode=Consumable» и тащит инвентарную машинерию (накопительный `held`), из-за чего «на руках» врёт (растёт вечно) и **прячет недовыдачу** (год1 1000 + год2 600 → held 1600 ≥ норма → зелёный, хотя в год2 недовыдали).

Инсайт заказчика: **расходник — это по сути нематериальное (контроль по ДАТЕ, как инструктаж), просто с количеством.** А инструктаж — это та же периодическая позиция с количеством «1 шт». Значит инструктаж и расходник — ОДИН тип.

**Успех:** инструктаж и расходник объединены в один тип «периодическая позиция» (количество обязательно, инструктаж = 1 шт); статус периодической = по дате + недовыдача по ПОСЛЕДНЕЙ выдаче (`последняя выдача < нормы → красный`), без накопления и без тающего баланса; «на руках» = последняя выдача; периодическая НЕ списывается; инвентарь (ботинки) остаётся отдельным типом (накопительный held, списание) без изменений поведения; `MaterialMode` исчезает; прод-данные мигрированы.

## 2. Модель — ДВА типа позиции (вместо Material+mode / NonMaterial)

1. **Инвентарь** (`ComplianceType::Material`, бывш. mode=Inventoried): долговечная выдача (СИЗ: ботинки). Количество + срок. `held` = **накопительный** (Σ выдач − списания). Контроль: `held < норма → красный` + срок. **Списывается** (акт списания).
2. **Периодическая** (`ComplianceType::Periodic`, бывш. NonMaterial ∪ Material/Consumable): инструктаж, медосмотр, ДСИЗ. Количество **обязательно** (инструктаж = 1 шт; крем = 1200 мл) + срок. `held` = **последняя выдача** (не копится, не тает). Контроль: `последняя выдача < норма → красный` (недовыдача) + срок. **НЕ списывается**.

Различитель при заведении требования: «долговечное, накапливается, списывается» (инвентарь) vs «каждый период заново, не списывается» (периодическая). `Requirement` остаётся мономорфным — одно требование целиком инвентарное ИЛИ периодическое.

Отвергнуто: «тающий held» (скользящее окно `effectiveHeld`) — неоправданное усложнение; натягивало инвентарную модель на расходник. Недовыдачу ловит и простая проверка «последняя выдача < нормы», накопительную инфляцию убирает «held = последняя выдача».

## 3. Дизайн по областям

### 3.1 Типы (`ComplianceType` + классы позиции)
- `ComplianceType`: `Material` (значение `'material'`, семантика теперь = **инвентарь**; title «Выдача») + НОВЫЙ `Periodic` (значение `'periodic'`, title «Периодическая»); `NonMaterial` **удаляется** (мигрирует в `Periodic`). `requiresQuantity()` → true для ОБОИХ (у периодической количество обязательно). `makeItem`: Material→`MaterialItem`, Periodic→`PeriodicItem`.
- `MaterialItem`: теряет `mode()`/`MaterialMode`; остаётся `quantity()` (обязательное). Семантика — инвентарь.
- НОВЫЙ `PeriodicItem extends AbstractRequirementItem`: + `quantity(): Quantity` **обязательное** (инвариант в конструкторе: количество > 0; инструктаж = 1 шт). `type()` = `Periodic`. jsonSerialize/fromArray с quantity (как у `MaterialItem`, но без mode).
- `NonMaterialItem` **удаляется**. `MaterialMode` enum **удаляется** (нет расходного режима — расходник теперь `PeriodicItem`).
- `RequirementItemsType` (jsonb DBAL): `makeItem` по типу требования — без дискриминатора, как сейчас.
- **Ортогонально и НЕ трогаем:** журнал инструктажа — это `Requirement::getJournalKind()` (+ `InstructionDetails` на факте, выбор `recordInstruction` vs `recordIssuance` в хендлере). Это отдельный флаг требования, НЕ завязан на `ComplianceType`. Периодическое требование МОЖЕТ нести `JournalKind` (инструктаж с .docx-журналом) или нет (медосмотр/ДСИЗ без журнала). Унификация типа позиции этого не касается — `JournalKind`/`InstructionDetails`/выбор record-метода остаются как есть.

### 3.2 Статус/held (резолвер + проектор)
- `held` по типу: инвентарь — Σ−списания (как сейчас); периодическая — **количество последней выдачи** (проектор: для периодической строки `held` = quantity самого свежего факта по ключу, не Σ).
- `ComplianceBucketResolver::bucketFor` — ladder «held < норма → Missing» + даты. Разница только в том, ЧТО такое held (считает проектор), и в ПОРЯДКЕ проверок по типу:
  - **Инвентарь:** как сейчас — недовыдача (held<норма) → Missing имеет приоритет (количество первично).
  - **Периодическая (РЕШЕНО): ДАТА ПЕРВИЧНА.** Срок истёк (`nextDueAt < now`) → Overdue (пора перевыдать), независимо от количества; в пределах срока, но последняя выдача < норма → Missing (недовыдача); иначе Soon/Ok по сроку. Резолвер ветвит порядок по типу позиции (нужен признак типа в `ObligationView`/строке проекции — тип уже есть в проекции).

### 3.3 Списание
- `writeOffEligibleFactsForRequirement` / `consumableKeys`: расходный флаг-отсев **уходит** — списанию подлежит ТОЛЬКО инвентарь (`MaterialItem`), периодическая структурно не материальна → не попадает. `MaterialMode::writeOffApplicable`/`isConsumable` удаляются вместе с enum.

### 3.4 Выдача (инвариант)
- `ProfileCompliance::assertIssuable` / `recordIssuance`: порог «на руках+выдача ≥ норма» для инвентаря — как есть (по накопительному held). Для периодической — проверка по ПОСЛЕДНЕЙ выдаче: сама выдаваемая строка `< норма → красный`-состояние (не блок выдачи, а статус). Единицу сверяем для обоих. (Инструктаж: норма 1 шт, выдача 1 шт.)

### 3.5 Форма требования
- Выбор типа требования: «Выдача (инвентарь)» / «Периодическая» (вместо Material/NonMaterial + под-выбор mode). У периодической поле количества — **обязательное** (для инструктажа дефолт «1 шт», единица «шт»). Убрать UI режима Inventoried/Consumable. Копировать разметку ближайшего аналога, новых стилей не вводить.

### 3.6 Проекция/отображение
- Строка проекции несёт `held` по правилу типа (проектор считает). **`mode`-колонка проекции — РЕШЕНО: оставить nullable**, перестать писать (расходного режима нет); физический дроп — отдельной поздней миграцией (как с tracked_obligation). `MaterialMode` enum в КОДЕ удаляется.
- «на руках» у периодической = последняя выдача (осмысленно, напр. крем «1200 мл»). **Количество инструктажа (1 шт) — РЕШЕНО: ПРЯТАТЬ** (как сейчас нематериальное: инструктаж контролируется по дате, число «1 шт» на экране не показываем). Признак «прятать количество» — по сути «норма = 1 шт / единица шт» или по отсутствию смысловой величины; в плане уточнить предикат (вероятно: прятать, если позиция периодическая И единица = «шт» И норма = 1).

## 4. Миграция данных

Идемпотентная миграция jsonb `compliance_requirement.items` + `compliance_requirement.type`:
1. Требования `type='non_material'` → `type='periodic'`; каждой позиции добавить `quantity = {amount:1, unit:'шт'}` (инструктаж = 1 шт).
2. Требования `type='material'`, все позиции которых `mode='consumable'` → `type='periodic'`; позиции сохраняют `quantity`, поле `mode` убрать.
3. Требования `type='material'` с позициями `mode='inventoried'` (или без mode) → остаются `material` (инвентарь); убрать поле `mode` из позиций.
4. **Смешанные** требования (material c И инвентарными, И расходными позициями) — на проде проверить, что таких НЕТ (пред-проверка; требование мономорфно по смыслу). Если есть — разнести вручную/флагом (в плане).
5. Проекция: после миграции — `app:compliance:rebuild-projection` (periodic-строки получат held=последняя выдача; mode перестанет использоваться).
6. Единица «шт» для инструктажа — сверить, что `Unit` такой enum-case есть (иначе добавить).

## 5. Тесты

- `PeriodicItem`: конструктор (quantity обязательно > 0; инструктаж 1 шт), round-trip jsonb.
- `ComplianceType`: `Periodic` makeItem; удаление `NonMaterial` не ломает (мигрировано).
- Резолвер/проектор: периодическая held = последняя выдача; недовыдача (последняя < норма) → красный; доввыдача НЕ копится (последняя < норма → всё ещё красный, пока не выдашь ≥ норма одной выдачей); срок истёк → красный; инструктаж (1 шт) прошёл/не прошёл.
- Инвентарь: накопительный held + списание — регресс не сломан.
- Списание: периодическая НЕ попадает в корзину (структурно).
- Выдача: assertIssuable периодической/инвентаря.
- Миграция: non_material→periodic (+1 шт); material/consumable→periodic; material/inventoried остаётся; смешанных нет (пред-проверка).

## 6. Решения (из ревью спеки) + остаток в план

- **РЕШЕНО 1 — bucket периодической: ДАТА ПЕРВИЧНА.** Истёк срок → Overdue (независимо от кол-ва); в сроке, но недовыдал → Missing. Порядок проверок в резолвере ветвится по типу (§3.2).
- **РЕШЕНО 2 — количество инструктажа ПРЯЧЕМ** на экране (контроль по дате), как сейчас нематериальное (§3.6).
- **РЕШЕНО 3 — `mode`-колонку проекции оставить nullable** (перестать писать), `MaterialMode` enum в коде удалить; физический дроп колонки — поздней миграцией (§3.6, §4).
- Остаётся в план: title для `Material`-инвентаря («Выдача» vs «Выдача (инвентарь)») — косметика; точный предикат «прятать количество» (периодическая + шт + 1); пред-проверка смешанных material-требований на проде (ожидаем 0) и план действий если найдутся.

## 7. Вне охвата (non-goals)

- «Тающий held» / скользящее окно — отвергнут.
- D6 (ответственные/комиссия→profileId) — отдельный деплой, после.
- Переосмысление инвентарной модели (ботинки) — не трогаем.

## 8. Риски

- **Смешанные требования** (material с инвентарём+расходником) ломают мономорфную миграцию — митигируем пред-проверкой на проде (ожидаем 0 на 3 требованиях).
- **Единица «шт» у инструктажа** — если в `Unit` нет подходящего case, добавить; иначе миграция инструктажей упрётся.
- **Регресс инвентаря** — убирая mode, не задеть инвентарную ветку (held/списание). Митигируем тестами инвентаря.
- **Проекция held периодической** — проектор должен брать именно ПОСЛЕДНЮЮ выдачу, не Σ; тест на доввыдачу (не копится).

## 9. Декомпозиция

Один деплой, один план (через writing-plans). Ориентир задач (TDD): (1) `PeriodicItem` VO + `ComplianceType::Periodic` + `makeItem`, инвариант количества; (2) снять `MaterialMode` с `MaterialItem` + из списания (структурный отсев); (3) held периодической = последняя выдача в проекторе + bucket-порядок (§6.1); (4) форма требования (инвентарь/периодическая, количество обязательно); (5) отображение «на руках»/инструктаж; (6) миграция данных jsonb (non_material→periodic +1шт, material/consumable→periodic, убрать mode) + rebuild + пред-проверка смешанных; удаление `NonMaterialItem`/`MaterialMode`. Детализация — в плане.
