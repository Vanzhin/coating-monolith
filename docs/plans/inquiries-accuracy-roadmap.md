# Inquiries: как со временем получать более точные и одинаковые ответы

Дата: 2026-10-29. Статус: обсуждение, не план реализации. Планы по шагам — отдельными файлами (`inquiries-7-*`, `inquiries-8-*`).

## Что уже есть и на что опираемся

- Порт `InquiryParametersExtractor` → `NetAngelsExtractor`; промпт `system-prompt.v3.txt` статичный (14 КБ правил), `temperature: 0`, `response_format: json_object`.
- Порт `ApprovedParameterCache` — заглушка `Noop`; план 5 (`inquiries-5-templates-and-cache.md`) описывает семантический кеш и шаблоны.
- Пер-полевой провенанс: `RecognizedParameters` хранит для каждой оси origin (Model / Cache / Manual), `withManualEdits` помечает реально изменённые инженером оси. `Approved` — терминальный статус с `Verification`.
- `ParameterSource.details` хранит модель, версию промпта, токены, время.

Итого: с первого дня накапливаются пары «текст → что сказала модель → что одобрил инженер» с пометкой, какие оси правились. Это материал для всех механизмов ниже.

## Две разные задачи

- **Точность** — ответ модели ближе к тому, что одобрит инженер.
- **Одинаковость** — похожие входы дают одинаковые параметры; один и тот же вход при повторе даёт тот же ответ.

У них разные инструменты. Ниже — по силе эффекта и в порядке реализации.

## 1. Эталонный набор и измерение

Без этого нельзя сказать, стало ли лучше. Эталон — одобренные запросы: собранный текст + финальные параметры инженера.

Консольная команда прогоняет текущий промпт и модель по эталону и считает по каждой оси: совпало / модель дала лишнее / пропустила / инженер поправил. Выход — таблица точности по осям.

Даёт:
- видно слабые оси (ожидаемо: температуры, `durability`);
- каждая версия промпта проверяется на регрессию по эталону до выкатки, не на живых инженерах;
- измерение нестабильности: один текст прогнать 5 раз, сравнить. Расходится при `temperature: 0` — проблема не промпта (см. п. 4).

Делать первым. Данные в базе, команда — на вечер.

## 2. Динамические примеры из одобренных (главный рычаг точности)

Сейчас модель решает «с нуля» по правилам промпта. Правила — слабый способ учить: каждый частный случай — новая строка, промпт растёт, модель всё равно трактует по-своему.

Сильнее — показывать примеры решений. Перед вызовом берём 3–5 одобренных запросов, наиболее похожих на текущий текст (по эмбеддингам), и вкладываем в промпт: «вот текст — вот параметры, которые извлёк инженер». Модель подстраивается под практику, включая неписаные правила инженеров.

Даёт и точность, и одинаковость: похожие входы притягиваются к одним примерам → к одним ответам. Безопаснее кеша: модель читает реальный текст, «этанол при 40» и «этанол при 90» не схлопываются.

В коде:
- `SystemPromptBuilder` → составной: постоянная часть (правила, схема) + блок примеров.
- Новый порт `ApprovedExamplesProvider::findSimilar(type, text, k)`; реализация — pgvector в Postgres.
- `ApproveInquiryCommandHandler` уже вызывает `cache->index($inquiry)` — туда встаёт расчёт эмбеддинга и запись в индекс.
- В `ParameterSource.details` — id примеров, которые видела модель (для разбора: какие соседи увели).

Проверить: есть ли у NetAngels endpoint эмбеддингов. Нет → локальная модель эмбеддингов (CPU) или Yandex. Через порт.

## 3. Петля правок → правила промпта

Провенанс `Manual` по осям — готовый отчёт: «за месяц поправили `thermal.maxTemperature` в 23 из 80, `substrates` — в 4».

Раз в месяц: самая исправляемая ось → читаем 10–15 случаев → находим закономерность → формулируем правило → новая версия промпта → прогон по эталону (п. 1) → если ось выросла, остальные не упали — выкатываем.

Ручной процесс, но управляемый данными. Пункт 2 снижает потребность в нём.

## 4. Детерминизм (одинаковый вход → одинаковый выход)

- **Закрепить версию модели.** `qwen3.8-flash` — псевдоним, провайдер может подменить веса. Если есть датированные снапшоты — указывать явно; иначе фиксировать в `ParameterSource` и следить за сдвигом по эталону.
- **`json_schema` вместо `json_object`,** если шлюз поддерживает: убирает вариативность формы (лишние поля, строки вместо чисел).
- **`seed`,** если провайдер принимает — вместе с `temperature: 0` почти полная повторяемость.
- **Больше детерминированного вне модели.** Уже есть `SubstanceResolver`. То же для температур: регулярка вынимает числа с °C; модель вернула температуру, которой нет в тексте → предупреждение; в тексте есть, модель вернула null → предупреждение. Модель предлагает, код проверяет.

## 5. Семантический кеш (план 5) — последним

Даёт максимальную одинаковость: тот же вопрос — тот же ответ без модели. Но:
- **Замораживает ошибки.** Одобрили не глядя → кеш раздаёт неточность всем похожим, модель уже не исправит.
- Риск схлопывания разных запросов (в плане 5 — проверка ключевых сущностей, ещё один слой со своими ошибками).

Включать, когда эталон показывает стабильно высокую точность и правок почти нет. Тогда это экономия и ускорение, а не закрепление текущего качества.

## Не делать сейчас

**Дообучение модели.** Нужны тысячи примеров, привязывает к провайдеру (против порта), при изменении схемы фильтра — переобучать. Возвращаться при >1000 одобренных и когда п. 2–3 перестали давать прирост.

## Организационное условие

Петля учится на одобрениях. «Одобрить» не проверяя → система учится на шуме и закрепляет ошибки. Договориться: одобрение = «проверил и согласен», не «закрыть запрос».

Смотреть на расхождения между инженерами: двое на похожих запросах решают по-разному → модель будет метаться. Это правило надо согласовать между людьми, не в промпте.

## Порядок

1. Эталонный набор и команда измерения.
2. Эмбеддинги + динамические примеры в промпте.
3. Ежемесячная петля правок → промпт, проверка по эталону.
4. Детерминизм: версия модели, `json_schema`, `seed`, проверки регулярками.
5. Семантический кеш — на плато точности.
