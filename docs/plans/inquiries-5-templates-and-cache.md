# План (эскиз, позже): Inquiries — разбор без модели (семантический кэш + шаблоны)

Деплой 5. Делается ПОСЛЕ накопления данных в проде через [1-4]. Опирается на хранение из [плана 3](inquiries-3-engine-and-storage.md). Движок и веб/почта НЕ меняются — всё за существующим портом `InquiryParametersExtractor` (цепочка стратегий перед LLM). Цель: расходы на модель ↓, точность ↑ **по мере наполнения базы** (каждый одобренный запрос делает систему точнее и дешевле).

## Что значит «похожий запрос»

НЕ одинаковый текст и НЕ одна форма. **Один и тот же вопрос по сути**, разными словами и объёмом:
«дайте для этанола» ≡ «тут простыня из парсера, но суть — покрытие для этанола». Текстом/хешем это не поймать — суть в том, что оба дают **одни параметры подбора**. Канон запроса — его параметры (вещество/подложка/среда/температура), а не буквы.

## Цепочка стратегий за портом (первая УВЕРЕННАЯ отвечает)

1. **Точный дубль — хеш содержимого.** Байт-в-байт тот же вход (файл/нормализованный текст) и результат одобрен → отдаём сохранённый. Дёшево, безопасно.
2. **Семантический кэш — эмбеддинги.** Эмбеддим текст запроса дешёвой embedding-моделью (на порядки дешевле полного chat-completion) → векторный поиск по эмбеддингам **одобренных** прошлых запросов → близкий по смыслу (косинус выше порога) → переиспользуем его параметры, дорогое извлечение пропускаем.
3. **Шаблонный разбор — для частотных ФОРМ** (опросники ОНХП `…-П-ОЛ…`): узнаём форму по сигнатуре → детерминированные правила по `pdftotext -layout`-тексту.
4. **NetAngels (LLM)** — фолбэк для реально новых/неуверенных.

## Семантический кэш — как не схлопнуть разные запросы

«Этанол при 40» и «этанол при 90» семантически близки, но это РАЗНЫЕ запросы. Защита:
- **высокий порог** косинусного сходства;
- эмбеддинг даёт только КАНДИДАТА; подтверждаем **дешёвой детерминированной сверкой ключевых сущностей** (имена веществ + температуры + подложка) между новым входом и кандидатом — числа/вещества должны совпасть. Для этого ключевые сущности из входа вынимаем дёшево (словарь веществ + регэксп температур), без полного LLM;
- совпали эмбеддинг И ключевые сущности → переиспользуем; расхождение/сомнение → в LLM. Лучше лишний дешёвый эмбеддинг и честный вызов модели, чем неверный переиспользованный ответ.
- переиспользуем ТОЛЬКО **одобренные инженером** результаты — отдаём человеко-проверенное, не свежую догадку.

## Что для этого обязано храниться (из [плана 3](inquiries-3-engine-and-storage.md))

С первого дня, чтобы к плану 5 всё было готово:
- **текст запроса** (склеенный) + его **эмбеддинг** (вектор) — для семантического поиска;
- **хеш** содержимого — для точных дублей;
- **сигнатура документа** — для шаблонов;
- **извлечённые параметры** + **нормализованные ключевые сущности** (вещества/температуры/подложка) — для сверки кандидата;
- **правки инженера** + флаг **«одобрено»** — только одобренное идёт в кэш;
- **какой стратегией** получен результат (cache/semantic/template/llm) — для метрик экономии.

## Петля самоулучшения

```
новый вход → (хеш? семантика? шаблон?) нет → LLM → инженер проверил/поправил → ОДОБРИЛ
   → сохранили: текст+эмбеддинг+хеш+сигнатуру+параметры+ключевые сущности
   → следующий тот же по СМЫСЛУ запрос → семантика находит одобренного соседа → без модели, точно
```
Чем больше одобренных запросов в базе — тем больше вопросов закрывается без модели и тем выше консистентность ответов. Точность и экономия растут с наполнением БД.

## Развилки (на момент реализации)

- **Embedding-модель**: та же NetAngels (если есть embeddings-эндпоинт) / локальная (дёшево, приватно) / Yandex. Через порт — провайдер-независимо.
- **Векторное хранилище**: pgvector на Postgres (уже наша БД) vs Elasticsearch (уже есть в проекте, умеет kNN). Предпочтение — pgvector, если тянем расширение; иначе ES.
- Порог сходства + состав «ключевых сущностей» для сверки — калибруем на накопленном корпусе.
- Инвалидция при смене версии промпта/правил извлечения (старые одобренные — другой схемы).
- Сканы/фото (нет текста) — сюда не относятся, им нужен OCR/vision (отдельная ветка).
