# Импорт систем покрытий из docx-файлов

## Задача
Перенести системы покрытий из 6 docx-файлов (`~/Downloads/системы/251106_Системы *.docx`)
в БД. Всего распарсено **105 систем** (Мосты, Нефтегаз, Энергетика, Гидротехника,
Промка, Огнезащита).

## Подход
docx на PHP не парсим (хрупко, лишняя зависимость). docx приводится к чистому
нормализованному JSON скриптом (разово, вне репо), JSON коммитится в репозиторий
как источник истины импорта. Консольная команда читает JSON и по каждой системе
диспатчит существующий `CreateCoatingSystemCommand` через `CommandBus` — вся
доменная валидация (совместимость слоёв, DftRange, лимит слоёв) работает как есть.

Резолв «материал из файла → покрытие в БД» делается **в PHP против живой БД** в
момент импорта, а не запекается в JSON. Поэтому после добавления недостающих
покрытий повторный прогон подхватит ранее заблокированные системы без правки данных.

## Принятые решения (развилки согласованы с пользователем)
- **Подготовка поверхности** (в файлах отсутствует, доменом обязательна): резолв по
  подложке, не по коду. Подготовки под бетон/оцинковку/напыление в реальности не имеют
  кода-стандарта (в отличие от стальных `Sa`/`St`/`Wa`), поэтому команда выбирает так:
  1) явный флаг `--surface-treatment CODE` — жёсткое переопределение, обязан покрывать
  подложку; 2) код из JSON (`Sa 2 1/2`), если его подготовка покрывает подложку системы
  (углеродистая сталь → `Sa 2 1/2`, как раньше); 3) иначе — первая подготовка, чей
  `substrate_scope` покрывает подложку (бетон/оцинковка/напыление → соответствующая
  бескодовая подготовка). Нет подходящей → `failed`. Коды и JSON под не-стальные системы
  не правим.
- **Подложка** (в файлах нет как поля): авто из заголовка-объекта секции.
  Маппинг по ключевым словам: `бетон`→concrete, `металлизац/напыл`→steel_metallized,
  `оцинков`→steel_galvanized, `нержаве/алюмин`→aluminum, иначе→steel_carbon.
  Запечена в JSON (поле `substrate`), т.к. выводится из заголовка, которого в БД нет.
  Один неоднозначный объект («нержавеющая + оцинкованная + алюминий + металлизация»)
  помечен `substrateAmbiguous: true`, дефолт steel_metallized.
- **Среда эксплуатации** (в файлах нет как поля): авто из заголовка-объекта секции,
  запечена в JSON (поле `environment`) — как подложка. Кураторская разметка 21 заголовка:
  `immersion` (15) — погружение/шпунты-сваи, внутренняя поверхность РВС, внутренние
  стенки резервуаров с водой/мазутом/маслом, заглублённые циркводоводы с морской водой,
  сваи угольных причалов; `special` (15) — повышенные температуры (в т.ч. 120-600°C),
  огнезащита одно/двухкомпонентная; `atmospheric` (75) — всё остальное, включая (решение
  пользователя) «атомные объекты», «маркировочную окраску дымовых труб», наружную
  поверхность РВС. Спорный «Металлоконструкции котла… + резервуары воды» (Энерг №1-4) —
  atmospheric (ведущее «металлоконструкции котла», объекты наружные). Пустое/неизвестное
  значение среды в JSON → `failed` (опечатку данных не глушим в atmospheric).
  Рефактор Coating сделал среду измерением: чип поиска систем + расчёт интервала перекрытия.
- **ТСП из диапазона** («60-80»): берётся **максимум** (80). Одиночное значение — как есть.
- **Название** (явной колонки нет): `«{Файл} №{n}»`, напр. «Мосты №1».
- **Альтернативы в ячейке** («Литакоут Фрост/ Литакоут Флекси»): берётся первая
  альтернатива, которая есть в БД.
- **Описание**: колонка «Описание» + «Срок службы» из файла, обрезка до 2000 символов.

## Данные, которые НЕ импортируются
- Compliance/стандарты («Входит в СТО-...») — вычисляются `ComplianceEvaluator` из
  слоёв автоматически, в описании остаются как текст.
- Теги — в этой задаче не импортируем (climate-категории У1/ХЛ1 остаются в описании).

## Что не импортируется по объективным причинам (репортится, не гадаем)
- **Огнезащита, ТСП «По ПТМ»** (8 систем): толщина огнезащиты определяется расчётом,
  не фиксированное число. В доменную модель (int в пределах DftRange) не ложится —
  пропуск с причиной «ТСП не числовой».
- **23 системы заблокированы** отсутствующими в БД покрытиями (пользователь добавляет):
  Литапрайм Сил (8), Литамастик 280 (6), Литатерм Цинк ЭС (3), Литатанк Стронг (2),
  Литакоут Флекси (1), Литапрайм Экспресс Алкид (1), Литамстик 290 (опечатка, 1),
  Литалак Фрост (1), Литакоут Эпокс (1).

## Файлы
- `app/src/Coatings/Infrastructure/Console/Resources/coating_systems.json` — данные (105 систем,
  каждая с полями `substrate` и `environment`, выведенными из заголовка секции).
- `app/src/Coatings/Infrastructure/Console/ImportSupport.php` — чистые хелперы
  (`normalizeTitle`, `maxDft`).
- `app/src/Coatings/Infrastructure/Console/ImportCoatingSystemsCommand.php` — команда
  `app:coating-system:import` (`--file`, `--surface-treatment`, `--dry-run`).
- `tests/Unit/Coatings/Infrastructure/Console/ImportSupportTest.php` — юнит-тесты хелперов.

## Поведение команды
1. Грузит все покрытия → карта `нормализованный title → coatingId`.
2. Грузит surface_treatment → карта `code → id`, берёт заданный код.
3. Грузит существующие системы → множество занятых названий (идемпотентность).
4. По каждой системе из JSON:
   - title уже занят → `skipped (exists)`.
   - слой не резолвится (нет покрытия / ТСП не числовой) → `blocked`, причина; система целиком пропущена.
   - иначе `CreateCoatingSystemCommand` → `commandBus->execute`; доменная ошибка
     ловится по-системно → `failed` + сообщение (весь прогон не падает).
5. Итог: created / skipped(exists) / blocked / failed с расшифровкой.

`--dry-run` — только печатает резолв, ничего не пишет.

## Проверка
- Юнит-тесты хелперов (хост): 9/9. Весь unit-набор Coatings: 330/330.
- phpstan/cs-fixer по новым файлам — чисто.
- Реальный прогон на локальной БД, идемпотентность подтверждена (повтор: 0 создано).
- Спот-чек «Мосты №1»: слои ЛИТАПРАЙМ Цинк 80@80 → Экспресс МИО@140 → ЛИТАКОУТ Фрост@60
  (ТСП=макс, альтернатива Фрост/Флекси→Фрост, порядок слоёв верны).

## Результат первого прогона (локальная БД)
`создано: 62 | заблокировано: 30 | ошибок: 13` (итого 105).

- **62 создано** — все с подложкой `steel_carbon` (единственная, для которой в БД есть
  совместимая подготовка).
- **30 заблокировано**: 23 — нет покрытия в БД (9 материалов, пользователь добавляет);
  7 — Огнезащита с ТСП «По ПТМ» (расчётная толщина, в доменную модель не ложится).
- **13 ошибок доменной валидации** (реальные конфликты правил, не баги команды):
  - **10 систем на бетоне**: подготовка «Sa 2 1/2» scoped на `steel_carbon`, а подложка
    Бетон. В БД НЕТ ни одной подготовки для не-стальных подложек (все 11 — `steel_carbon`).
    → пользователю: завести подготовки для бетона/оцинковки/металлизации, затем повтор.
  - **3 системы**: ТСП вне DftRange покрытия — Гидротехника №17 (320>300, ЛИТАМАСТИК
    Универсал 20, одиночное значение); Нефтегаз №9 и Энергетика №9 (125/150 мкм ×2 слоя
    ЛИТАТАНК Стандарт при паспортных 200–300 — источник тоньше диапазона продукта).
    → сверить исходный ТСП / подобранное покрытие вручную.

## Текущее состояние (dry-run против живой БД)
`будет создано: 95 | заблокировано: 10 | ошибок: 0` (итого 105).

Пользователь долил недостающие покрытия и подготовки для не-стальных подложек — доменных
ошибок (13 на первом прогоне) больше нет. Осталось 10 заблокированных, все — осознанный
пропуск по решению пользователя:
- **7 Огнезащита «По ПТМ»** — расчётная толщина, не число; в доменную модель (int в DftRange)
  не ложится. Доменную поддержку расчётной огнезащиты пока **не заводим**.
- **3 системы без покрытия в БД**: Огнезащита №3 (Литапрайм Экспресс Алкид), Энерг №19
  (Литалак Фрост), Энерг №21 (Литакоут Эпокс). Эти покрытия пока **не добавляем**.

Все 95 годных систем импортируются с корректной средой эксплуатации. Повторный прогон
идемпотентен по названию; если позже добавить 3 покрытия — они подхватятся без правки данных.
