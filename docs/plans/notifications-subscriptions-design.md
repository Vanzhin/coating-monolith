# Подписки на события + уведомления — дизайн (Фаза 1: общая система подписок)

**Статус:** дизайн-спека (согласована в брейншторме). Реализацию дробим на план(ы) после апрува.

**Цель:** общая для всего приложения система, где пользователь **подписывается на типы событий** и выбирает **каналы доставки** (inbox / web-push / email). События адресные: каждый получает только то, что касается его роли/связи. Часть типов — **системные** (нельзя отписаться: смена пароля, анонс фичи, безопасность), часть — **настраиваемые** (opt-in).

**Границы:** Фаза 1 — каталог типов + подписки + резолв адресатов + доставка (inbox/push/email) + экран настроек. Фаза 2 (отдельная спека/план) — «проходчик»: lead-time на норме, планировщик, daily-скан `nextDueAt`, генерация compliance-событий, антифлуд.

---

## 1. Контекст: что уже есть и чего не хватает

**Есть (переиспользуем):**
- Контекст `App\Notifications\` — агрегат `Notification` (`ownerUlid`, `message`, `isRead`), инбокс-UI (`/cabinet/notifications`), счётчик непрочитанных (Twig `unread_notifications_count()`).
- Доставка: `Shared\...\NotifierInterface` + `NotifierFactory` + `ChannelNotifierService` — `EmailNotifier` / `TelegramNotifier` / `WebPushNotifier` (web-push в проде работает, VAPID).
- Каналы-адреса пользователя: `App\Users\Domain\Entity\Channel` (`ChannelType`: TELEGRAM/EMAIL/WEB_PUSH; web-push per-device; email/telegram с верификацией).
- Событийная шина: `EventBus` (async через Redis), хендлеры по интерфейсу `EventHandlerInterface`, `DispatchAfterCurrentBusStamp` (события после commit), воркер `manager_supervisor`.
- Связь профиль→юзер: `Profile.userUlid`; начальник отдела: `Department.headUserUlid` (это User ULID).

**Чего нет (создаём в Фазе 1):**
- Каталога типов событий, деления системные/настраиваемые.
- Пользовательских подписок (user × тип × канал).
- Резолва адресатов события (кому слать).
- Подключения email и inbox как управляемых каналов в фан-аут (сейчас `Notification` → только web-push, автоматически).
- Экрана настроек подписок.

**Чего нет (Фаза 2):** планировщика/крона и любого скана по времени; `responsibleFio` на актах — свободный текст, не ссылка на User.

## 2. Ключевые понятия

- **Тип уведомления** (`NotificationType`) — case enum-каталога в коде. Метаданные типа: `label`, `category` (тематическая группировка для UI), `kind` (System|Configurable), `channels` (разрешённые каналы), `resolver` (стратегия адресатов), `visibleTo` (кому тип виден в настройках).
- **Вид (`kind`)** — `System` (принудительный, нельзя отписаться, дефолт «подписан») или `Configurable` (opt-in, дефолт «не подписан», можно выключить любой канал).
- **Подписка** (`Subscription`) — строка `user × тип × канал → вкл/выкл`. Только для настраиваемых. Системные в таблице не хранятся (всегда вкл по всем разрешённым каналам).
- **Канал** — `inbox` (запись `Notification` + бейдж), `web_push`, `email`. Абстракция доставки — существующий `NotifierInterface` (+ inbox как отдельный «канал-запись»).
- **Резолвер адресатов** — переиспользуемая стратегия «кому». Единицы на всё приложение: `Owner`, `SubjectSupervisors`, `Broadcast`. Тип ссылается на стратегию.
- **Уведомляющее событие** — доменное событие, реализующее маркер-контракт (отдаёт `notificationType()` + поля для резолвера/рендера).
- **Диспетчер** (`NotificationDispatcher`) — единый async-хендлер уведомляющих событий: тип → каталог → резолвер → адресаты → каналы по подпискам/системности → доставка.

---

## 3. Семантика: системные vs настраиваемые

| | Системные (`System`) | Настраиваемые (`Configurable`) |
|---|---|---|
| Можно отписаться | нет | да (любой канал, вкл. inbox) |
| Дефолт при появлении | подписан (все разрешённые каналы) | не подписан |
| Видны в настройках | нет (скрыты) | да (если доступны роли) |
| Хранение подписки | не хранится (всегда вкл) | строки `Subscription` |
| Примеры | смена пароля, анонс фичи, критичная безопасность | «СИЗ: подходит срок», «отчёт на проверке» |

Деление — одно свойство `NotificationType::kind()` + предикат `isSystem()`, протянутый в 4 места (по образцу dev-partner-group): (1) выбор каналов (системные → все разрешённые, минуя `Subscription`); (2) блок переключения в сервисе настроек (`toggleSetting` кидает ошибку для системных); (3) исключение из экрана настроек; (4) мягче доставка (системные — по любому каналу с адресом).

## 4. Резолв адресатов

**Принцип: событие адресное, не широковещательное.** Подписка = «получать события типа, **адресованные мне**». Событие несёт контекст (`ownerUlid` / `subjectProfileId`), резолвер по нему возвращает конкретный список `userUlid`. Доставка — тем из них, кто подписан (системное — всем). Кто не в списке адресатов — не получает ничего.

**Охват выводится из роли/связи, не настраивается пользователем.** Пользователь задаёт только вкл/выкл + каналы; *чьи* события придут — функция того, в какие списки-кандидаты кладёт резолвер.

**Стратегии (на весь проект, единицы):**
- **Owner** — адресат = пользователь из события (`ownerUlid`). Событие реализует контракт `OwnedNotification { ownerUlid(): string }`. Для «тебе выдали СИЗ», «пароль сменён».
- **SubjectSupervisors** — субъект (`Profile(subjectProfileId).userUlid`) + надзорные (все `ROLE_ADMIN` + начальник отдела субъекта `Department.headUserUlid`, если задан). Событие реализует `SubjectNotification { subjectProfileId(): string }`. Для «срок подходит», «просрочено».
- **Broadcast** — все пользователи (или все с ролью). Для «новая фича».

**Пример («срок подходит», событие `ComplianceDueSoon{ subjectProfileId: Иванов }`):**
- Резолвер `SubjectSupervisors` → кандидаты: Иванов (сам) + все админы + начальник отдела Иванова.
- Админ попадает в кандидаты **каждого** события типа → подписан → получает по всем (Иванов/Петров/Сидоров).
- Сидоров — кандидат только там, где он субъект → получает только свои.
- Начальник — только свой отдел.
- Путаница исключена архитектурно (рассылка не «всем подписчикам типа», а «адресатам события ∩ подписанные»).

**Роли на старте:** только `ROLE_ADMIN` / обычный. «Надзорные» = админы + начальник отдела (по `userUlid`, не по роли — поэтому расширение ролей его не ломает). Резолверы проектируем так, чтобы «надзорные = набор ролей/условий» легко дополнялся.

**Новый тип события** требует: (1) case в каталоге-enum (метаданные + ссылка на стратегию), (2) само событие (реализует контракт нужной стратегии + `notificationType()`), (3) рендер текста. Новый резолвер — редко (только принципиально новый способ адресации).

## 5. Поток доставки

1. В коде происходит уведомляющее событие (реализует `NotifiableEvent` + контракт стратегии), публикуется через `EventBus` (async после commit).
2. Единый `NotificationDispatcher` (хендлер, типизирован на интерфейс `NotifiableEvent` — Symfony Messenger роутит по реализуемым интерфейсам) ловит его.
3. По `event->notificationType()` берёт из каталога метаданные (kind, channels, resolver).
4. Резолвер стратегии → список адресатов (`userUlid`).
5. Для каждого адресата: какие каналы активны — системный тип → все разрешённые каналы, где у юзера есть адрес; настраиваемый → пересечение разрешённых каналов типа и подписок юзера (`Subscription.enabled`).
6. Рендер текста (`MessageRenderer` по типу, из полей события).
7. Доставка по каждому (адресат × канал): `inbox` → запись `Notification`; `web_push`/`email` → `NotifierInterface` на соответствующий `Users\Channel`.
8. (Фаза 1) резолв+доставка — в одном async-хендлере. При росте объёмов — разбить на «определить аудиторию» + per-channel job (как двухстадийный async в dev-partner-group).

**Согласование с текущим авто-пушем:** сейчас создание `Notification` само триггерит web-push (`NotificationCreatedEvent`). В новой модели push — это выбор канала, а не автоматика. Реконсиляция (деталь плана): inbox-запись `Notification` перестаёт автоматически пушить; web-push шлёт диспетчер только когда канал `web_push` активен у адресата. Прежний путь (`SendNotificationCommand`) либо мигрируем на диспетчер, либо оставляем как низкоуровневый «inbox+push» для системных.

## 6. Каналы и рендер

- **inbox** — запись `Notification(ownerUlid, message)`; это «источник правды» + бейдж. Для настраиваемых — отключаемый канал; для системных — всегда.
- **web_push** — `WebPushNotifier` на WEB_PUSH-каналы юзера (все устройства).
- **email** — `EmailNotifier` на EMAIL-канал юзера (подключаем в фан-аут; сейчас email используется только для кодов верификации).
- **telegram** — НЕ трогаем вообще (ни в Фазе 1, ни в каталоге каналов этой системы).
- **Рендер:** реестр `type → renderer(event): string` — на каждый тип события функция, превращающая данные события в текст уведомления (напр. `ComplianceDueSoon → "У Иванова И.И. подходит срок выдачи «Перчатки» — до 05.12.2026"`). Диспетчер зовёт рендерер типа и кладёт результат в инбокс/push/email. MVP — ОДИН текст на все каналы (у письма — дефолтная тема «Уведомление» + текст телом). «Контент на канал» (разные тема/html/кнопки для email vs короткий заголовок для push) — на будущее, в MVP не делаем.

## 7. Экран настроек

- Маршрут `/cabinet/notifications/settings` (или вкладка профиля). Доступ — авторизованные.
- Показывает **настраиваемые типы ∩ доступные роли пользователя**, сгруппированные по `category`. Системные **не показываются**.
- На каждый тип — переключатели каналов (`inbox` / `push` / `email` из разрешённых типу). Сохранение → строки `Subscription`.
- Дефолт: настраиваемый тип без строк = не подписан. Системные в списке отсутствуют.

## 8. Модель данных

**Код (каталог — enum, в `App\Notifications\Domain\Type\`):**
- `NotificationType: string` — cases + методы `label()`, `category(): NotificationCategory`, `kind(): NotificationKind`, `channels(): list<Channel>`, `resolver(): ResolverKey`, `visibleTo(): list<Role|predicate>`.
- `NotificationKind` — `System | Configurable` (+ `isSystem()`).
- `NotificationCategory` — тематика для UI (`Compliance`, `Reports`, `Security`, `System`, …).
- `Channel` — `Inbox | WebPush | Email` (маппинг на `Users\ChannelType` для push/email).
- `ResolverKey` — `Owner | SubjectSupervisors | Broadcast`.

**БД (новая таблица подписок):**
- `notification_subscription`: `id (uuid)`, `user_ulid (string)`, `type (string = NotificationType->value)`, `channel (string = Channel->value)`, `enabled (bool)`, `created_at`, `updated_at`. Уникальность `(user_ulid, type, channel)`. Миграция идемпотентная.
- `Notification` (существует) — не меняем структуру (инбокс). При необходимости — поле `type` для фильтрации инбокса (опционально, решим в плане).

**Контракты (Domain/Application):**
- `NotifiableEvent extends EventInterface { notificationType(): NotificationType; }`
- `OwnedNotification { ownerUlid(): string; }`, `SubjectNotification { subjectProfileId(): string; }`
- `RecipientResolverInterface { resolve(NotifiableEvent $e): list<string /*userUlid*/>; }` + реализации + реестр по `ResolverKey`.
- `Subscription` агрегат + `SubscriptionRepositoryInterface` (`findForUser`, `isEnabled(user,type,channel)`, `save`).
- `MessageRenderer` (реестр `type → renderer`).
- `NotificationDispatcher` (EventHandler на `NotifiableEvent`).
- Сервис настроек: `getConfigurableTypesForUser()`, `toggleSubscription()` (блок для системных).

## 9. Переиспользование vs новое

**Переиспользуем:** `Notification` (инбокс), `NotifierInterface`/`NotifierFactory`/`ChannelNotifierService`, `Users\Channel` (адреса), `EventBus`/воркер, счётчик непрочитанных, инбокс-UI.

**Новое:** каталог-enum + kind/category/channel/resolverKey, `Subscription` + репозиторий + миграция, резолверы + реестр, `NotificationDispatcher`, `MessageRenderer`, экран настроек + сервис, подключение email/inbox как каналов фан-аута, реконсиляция авто-пуша.

---

## 10. Границы MVP / пилот

- Полный слой: каталог + подписки + резолверы (3 стратегии) + диспетчер + 3 канала + экран настроек.
- **Один пилотный настраиваемый тип** для end-to-end (напр. `compliance.due_soon`), но событие в Фазе 1 кидаем из существующего места/вручную (команда-триггер), **без проходчика**.
- **Заложить место для системного типа** (напр. `security.password_changed` или `system.feature_announced`) — проверить принудительную доставку и скрытие из настроек.

## 11. Тестирование

- Юнит: `NotificationType` метаданные/kind/isSystem; резолверы (owner/subject+supervisors/broadcast) — состав адресатов на фикстурах (субъект+админ+начальник, чужой не попадает).
- Функц.: диспетчер end-to-end — событие → адресаты → каналы по подпискам (настраиваемый: не подписан → не доставлено; подписан push → inbox+push; системный → всем, отписка игнорируется). Owner-событие: чужому не приходит.
- Функц.: экран настроек — системные скрыты, toggle сохраняет `Subscription`, toggle системного → ошибка.
- `./run check` зелёный; async в тестах — как принято (хендлер зовём напрямую, т.к. `when@test` async не обрабатывает в процессе).

## 12. Фаза 2 (отдельная спека/план) — «проходчик»

- Lead-time на норме/требовании (напр. СИЗ = 2 мес до `nextDueAt`).
- Планировщик: Symfony Scheduler или cron-команда (сейчас крона нет — вводим). Вариант по образцу dev-partner-group: атрибут-крон + генерация, либо простая console-команда `app:notifications:scan-due` в cron контейнера.
- Daily-скан `TrackedObligation.nextDueAt` со «спецификацией дат» → кидает `ComplianceDueSoon` / `ComplianceOverdue` (которые подхватит система подписок Фазы 1).
- **Антифлуд:** хранить «когда последний раз алертили по обязанности/стадии», чтобы не слать каждый день (эскалация: напр. за 2 мес, за 2 недели, в день Х, потом раз в неделю при просрочке). Нужна таблица/поле состояния алерта.

## 13. Открытые вопросы / будущее

- **`responsibleFio` → User.** Ответственный из акта сейчас текст; чтобы адресовать ему — сделать ссылкой на User (отдельная работа). Пока «надзорные» = админы + начальник отдела.
- **Двухстадийный async** — при росте объёмов.
- **Поле `type` на `Notification`** — для фильтрации/иконок инбокса; решим в плане.
- **Явный выбор охвата** (админ: «все / мой отдел / конкретные») — пока автоматом по роли; добавим, если понадобится.
