# План: подбор систем покрытий по письму (подсказка инженеру)

## Идея

Инженер пересылает письмо заказчика на служебный ящик. Система извлекает из текста письма и вложений параметры подбора, прогоняет их через существующий фильтр систем покрытий и отвечает инженеру письмом: извлечённые параметры, список подходящих систем, ссылка на фильтр с подставленными параметрами. Ответ — подсказка, решение принимает инженер.

Что НЕ делаем в первой версии:
- автоответ заказчику
- автоматический перехват всей почты (только ручная пересылка)
- разбор сканов и фото (только текст письма и вложения с текстовым слоем)
- признаки «нашёл / предположил» — модель возвращает только то, что есть в тексте, остальное null

## Решения, принятые при обсуждении

- Модель: API NetAngels AI Studio (https://www.netangels.ru/cloud-platform/aistudio/), OpenAI-совместимый, оплата в рублях, договор для юрлица. Начать с `qwen3.8-flash`; при ошибках в полях — `qwen3.8-27b` / `gemma4-31b` / `qwen3.8-max`. Qwen3.7 не брать.
- Своя машина и аренда GPU не нужны.
- Сервис живёт внутри монолита как новый bounded context (условно `Inquiries`), не отдельным сервисом на Python.
- Цель извлечения — поля `CoatingSystemsFilter`: substrates, environment, standard, category, durability, thermalTemperature, thermalEnvironment, applicationMinTemp, minApplicationTimeAt20. Поиск — через существующий `findByFilter`, новой логики подбора нет.
- Модель отдаёт значения в терминах проекта (enum `Substrate`, `EnvironmentType`, категории C1…CX, срок L/M/H/VH). Что не попало в допустимые значения — null. Маппер JSON → DTO → фильтр — только shape, без бизнес-логики.
- Ящик принимает письма только с корпоративных адресов, остальное игнорируется.
- Каждый запрос сохраняется с первого дня — для разбора ошибок и будущей автоматики.

## Поток первой версии

1. Инженер пересылает письмо на служебный ящик (можно с комментарием в теле — модель его прочитает).
2. Консольная команда по крону (раз в минуту) забирает новые письма по IMAP. Защита от повторной обработки — по Message-ID.
3. Из письма берётся тело (включая пересланное письмо внутри) и вложения:
   - DOCX, XLSX, PDF с текстовым слоем → текст библиотекой, без модели
   - PDF без текста, JPG, PNG → пометка «скан, не разобрано»
   - длинные приложения (ГОСТы, спецификации) обрезаются по лимиту символов
4. Один запрос к модели: системный промпт (схема полей, допустимые значения, правило «нет в тексте — null», 2–3 примера) + текст. `response_format: json_object`, режим размышлений отключён.
5. JSON → маппер → `CoatingSystemsFilter` → `findByFilter`.
6. Ответное письмо инженеру (отправителю пересылки): извлечённые параметры, первые N систем со ссылками в кабинет, ссылка на страницу фильтра с подставленными параметрами, список неразобранных вложений.
7. Запрос сохраняется в базе со статусом.

## Хранение: агрегат «Запрос на подбор»

Цель — для любого письма пройти цепочку целиком и найти, на каком стыке ошибка.

1. Вход, как пришло:
   - отправитель, тема, дата, Message-ID
   - тело письма как есть
   - вложения: файлы в файловом хранилище; в базе — имя, тип, размер, ссылка, результат извлечения (текст получен / скан / ошибка чтения)
2. Что отдали модели:
   - ровно тот текст, который ушёл в запрос (после склейки и обрезки)
   - название модели, версия системного промпта (сами промпты — по версиям в коде или отдельной таблице)
3. Что модель вернула:
   - сырой JSON как есть
   - результат маппинга: какие значения приняты, какие отброшены как недопустимые
   - расход токенов, время ответа
4. Что ушло инженеру:
   - идентификаторы систем в порядке выдачи, их количество (не текст письма — он восстанавливается из шаблона; список систем со временем меняется)
5. Обратная связь инженера (минимально, но с первой версии):
   - ссылка на фильтр в письме несёт идентификатор запроса; если инженер поправил параметры и нажал «найти» — параметры сохраняются рядом как «исправленные инженером»

Статус: получено / разобрано / отправлено / ошибка на шаге N с текстом. Ошибка — запись в базе, не только в логе.

Разбор ошибок — по трём классам: извлечение текста из файлов, модель (сырой JSON), маппер (отброшенные значения). Для каждого класса — своё лечение.

## Размещение в проекте (DDD)

- `Inquiries/Domain` — агрегат Запрос (письмо, текст для модели, JSON, параметры, список систем, статус, правки инженера); правила вроде «нельзя отправить ответ без разобранных параметров».
- `Inquiries/Application` — хендлеры: принять письмо, разобрать, подобрать, отправить, сохранить правку инженера. Обращение к `Coatings` — через его публичный `findByFilter`.
- `Inquiries/Infrastructure` — IMAP-приёмник, извлечение текста из файлов, адаптеры модели (`Api/`), хранение файлов, отправка почты, админ-страница.

### Независимость от провайдера модели

Разбор текста — порт, а не клиент конкретного API. Смена провайдера не должна трогать ничего, кроме адаптера и строки в конфиге.

- Интерфейс в Application: `InquiryParametersExtractor::extract(InquiryText): ExtractionResult`. Говорит на языке задачи (текст → параметры), не на языке модели (messages, temperature).
- `ExtractionResult` — извлечённые параметры в терминах проекта + сырой ответ модели для хранения + VO с метаданными вызова (модель, версия промпта, токены, время).
- Адаптеры в Infrastructure: `NetAngelsExtractor` (сегодня), далее при необходимости `YandexExtractor`, `OllamaExtractor`. `FakeExtractor` — для тестов хендлеров без сети. Подмена — в `services.yaml`.
- В адаптере только то, что зависит от провайдера: URL, ключ, имена моделей, параметры (отключение размышлений), формат запроса/ответа, повторы при сетевых ошибках.
- Сборщик системного промпта — отдельный класс вне адаптера: это знание о предметной области, не о провайдере. Версионируется там же. Адаптер получает его через конструктор.
- Маппер JSON → параметры фильтра — отдельный класс вне адаптера: одна схема для всех провайдеров, отброшенные значения фиксируются в одном месте.

## Выводы из стенда `tesl_llm_self` (Ollama + Docling, разбор ТДС)

Стенд решает соседнюю задачу (характеристики из ТДС), но механика та же. Что берём:
- Извлечение текста: лёгкие парсеры (`pdftotext`, python-docx, openpyxl) дали 25 заполненных полей из 39, Docling — 24. Тяжёлый ML-парсер не нужен. PHP-аналоги: `spatie/pdf-to-text`, `phpoffice/phpword`, `phpoffice/phpspreadsheet`.
- JSON-схема как грамматика (модель не может выйти за структуру). У OpenAI-совместимых API — `response_format: {type: "json_schema"}`. Проверить поддержку у шлюза NetAngels; если есть — маппер проверяет только значения по enum, типы гарантированы.
- Правила промпта «только явно указанное», «нет — null», «только JSON без обрамления» — брать за основу.
- Кеш извлечённого текста по хешу содержимого вложения.

Ошибки модели 8B на русских ТДС, которые надо предусмотреть в промпте:
- путает смежные величины (толщина ↔ расход, твёрдость ↔ ударопрочность) → узкие однозначные описания полей, числовые поля числом, не строкой
- дублирует основные поля в `other` → схема закрытая, без `other`

Стенд можно использовать для этапа 1: подменить `prompt.txt` и `schema.json` на поля `CoatingSystemsFilter`, положить реальные письма в `docs/`, прогнать локально, затем тот же промпт отдать в NetAngels и сравнить.

## Обкатка промпта на реальных документах (2026-10-26)

Стенд вне кода (scratchpad): `pdftotext`/`phpspreadsheet` → текст → NetAngels (`https://ai.netangels.cloud/v1`, OpenAI-совместимый, `response_format: json_object`, `/no_think`) → JSON → разбор по enum'ам `CoatingSystemsFilter`.

**Результат.** Промпт обкатан и стабилен на 7 реальных документах: 5 опросников РВС (ОНХП, нефтепродукты), понтон, химписьмо с вложением XLSX. Модель `qwen3.8-flash` достаточна. Ключевой вывод: провалы оказались **не потолком модели** — `qwen3.8-flash` и `qwen3.8-27b` ошибались побайтово одинаково, значит лечатся **промптом**, а не более дорогой моделью.

**Журнал решений (контракт извлечения):**
- `substrates` — только материал ОКРАШИВАЕМОЙ конструкции, названный прямо (РВС → steel_carbon, Duplex → stainless_steel). Марки из таблиц «материальное исполнение оборудования» (09Г2С/AISI 304/алюминий по средам) НЕ брать. Не названо → `[]`.
- `environment` — вода/почва → `immersion`; всё остальное (нефтепродукты, кислоты, химия) → `special`; открытый воздух → `atmospheric`. **Нефтепродукт = special** (не immersion). При двух средах — ведущая (внутренняя с продуктом).
- `substances` — ВСЕ вещества, включая кислоты; ничего не отсеивать. «На кислоты нет рекомендаций» — бизнес-факт, отсев/логика по веществам решается ПРОГРАММНО ниже по конвейеру (вероятно, по одному веществу). Имена → резолв в `substanceIds` через `ChemicalResistance` (`SubstancesFilter.search` / `MatchSubstancesForSearch`).
- `durability` — только срок службы ПОКРЫТИЯ/АКП. Срок конструкции (понтона/резервуара) → `null`.
- `thermalTemperature` — только если указана числом в тексте; температуру очистки (пропарка) и климат региона не брать.
- `thermalEnvironment` — если задан `thermalTemperature`, обязателен (не null): горячий продукт → `immersion`. Фильтру нужны обе части (temp+env), иначе температурный фасет молча отключается.
- `thermalIncludingPeak` — true, если расчётная выше рабочей (90 vs 40). Пропарка тут не пик.
- `search` — ПОКА только «пропарка» (очистка паром → в полнотекст).
- `standard`/`category` — только дословно; «тяжёлая морская среда» ≠ CX → null.

**Дисциплина:** каждое изменение промпта гонять по ВСЕМУ набору документов (регресс) — новое правило легко ломает старое (ловили: `search` сломал `thermalTemperature`; правило `special` обнулило `thermalEnvironment`).

**Контракт фильтра** (`CoatingSystemListRequestMapper`): query-параметры `substrates[]`, `environment`, `standard`, `category`, `durability`, `thermTemp`+`thermEnv`+`thermPeak`, `substanceIds[]`+`substanceTemp`, `search`/`q`, `minApplicationTimeAt20` в ЧАСАХ (×60 в минуты). JSON → фильтр почти 1:1, кроме резолва имён веществ → `substanceIds` и часы/минуты.

**Дальше:** замкнуть петлю (JSON → резолв веществ → `findByFilter` → реальная выдача); тяжёлое пересланное письмо (Duplex/морская/UV/RAL — у UV/цвета нет поля в фильтре = дыра модели данных; бывает запрос на ВАЛИДАЦИЮ предложенной системы, а не подбор); многосценарные документы.

### Текущий системный промпт (обкатанная версия)

```text
Ты — инженер-технолог по антикоррозионным покрытиям. Тебе дают текст (письмо заказчика, опросный лист, техзадание, иногда с вложениями). Распознай условия эксплуатации и требования к защитному покрытию и верни их СТРОГО одним JSON по схеме ниже, в терминах нашего каталога.

Только JSON. Без markdown, без пояснений, без текста вокруг.

Два действия, не путай:

РАСПОЗНАВАНИЕ (нужно): читаешь описание как специалист и переводишь в термины каталога.
- «резервуар вертикальный стальной (РВС)», «стальная рама», «металлоконструкция» → подложка steel_carbon; «нержавеющая сталь», «Duplex» → stainless_steel.
- хранимый/рабочий продукт (дизель, нефть, нафта, химвещество) → в substances; среду эксплуатации определи по правилам поля environment ниже.

ВЫДУМЫВАНИЕ (запрещено): не возвращай значение без прямого основания в тексте.
- категорию коррозивности (C1..CX, Im1..Im4) и стандарт (ISO 12944 / СП 28) — только если названы дословно. «Тяжёлая морская среда» — это НЕ категория.
- срок службы — только если указан именно для покрытия.
- температуру — только если указана числом. Не придумывай.

Схема (значение вне списка = null):

{
  "substrates": массив из ["steel_carbon","steel_galvanized","steel_metallized","stainless_steel","concrete","aluminum","existing_coating"],
      // материал ОКРАШИВАЕМОЙ конструкции, названный прямо (РВС/резервуар/рама/металлоконструкция → steel_carbon; нержавейка/Duplex → stainless_steel; бетон → concrete).
      // НЕ бери марки/материалы из таблиц «материальное исполнение оборудования/трубопроводов» (09Г2С, AISI 304, алюминий, расписанные по средам) — это не подложка покрытия. Прямо не названо → [].
  "environment": "atmospheric" | "immersion" | "special" | null,
      // среда эксплуатации защищаемой поверхности:
      //   atmospheric — открытый воздух/атмосфера (вне помещения, на улице, под навесом).
      //   immersion — погружение ТОЛЬКО в воду или в грунт/почву.
      //   special — любой другой контакт с жидкостью/химией: нефтепродукты (дизель, нефть, газойль, нафта, бензин), кислоты, щёлочи, растворители, прочие химвещества.
      // Если сред две (продукт внутри ёмкости + атмосфера снаружи) — бери ВЕДУЩУЮ, более жёсткую (обычно внутреннюю, с продуктом).
  "substances": массив строк,
      // ВСЕ вещества, с которыми контактирует покрытие (хранимый/рабочий/воздействующий продукт, химсреды), названия как в тексте. Бери ВСЕ, включая кислоты — ничего не отсеивай и не фильтруй. [] если веществ нет.
  "search": строка | null,
      // свободная строка для полнотекстового поиска. ПОКА сюда ТОЛЬКО пропарку: если есть требование/упоминание очистки паром (пропарка, пропаривание) → "пропарка". Больше ничего в это поле не добавляй. Нет пропарки → null.
  "thermalTemperature": целое °C (-200..1000) | null,
      // температура продукта/поверхности В ЭКСПЛУАТАЦИИ, ТОЛЬКО если явно указана числом (рабочая или расчётная максимальная; пример: рабочая 40, расчётная 90 → 90). Не указана числом → null, НЕ придумывай.
      // Температуру ОЧИСТКИ (пропарка/промывка паром, напр. 210-240) и климатическую температуру региона НЕ бери.
  "thermalEnvironment": "dry_heat" | "immersion" | null,
      // КАК приходит тепло к покрытию. ВАЖНО: если thermalTemperature задан числом — thermalEnvironment ОБЯЗАТЕЛЬНО укажи, НЕ оставляй null. Выбор:
```
