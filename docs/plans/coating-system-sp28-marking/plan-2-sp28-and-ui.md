# СП 28 маркировка — План 2: `Sp28Evaluator` + UI

> **СТОП — не начинать код по этому плану, пока не закрыты развилки.** До написания кода вернуться и
> явно решить: **A′** (требование для `WEAK`: максимум vs мягкое), **A** (маппинг Ц.7 — `ESI` II/III,
> `PAS`, нижняя граница диапазонов), **C** (вид СП-бейджа и отделение от ISO), **D** (`facets()` сейчас
> vs хардкод СП в Twig), **E** (cascade-семантика стандарта в finder). Значения в плане — черновые
> предложения, не финал. Детали каждой — в разделе «Развилки на ревью» ниже.

Второй деплой задачи. Опирается на План 1 (`plan-1-compliance-read-model-refactor.md`): к тому
моменту уже есть `ComplianceStandard`-enum, `Compliance` VO, `StandardEvaluator` (`supports()`+`evaluate()`),
патронаж `SystemComplianceEvaluator`, проектор пишет снапшот, показ читает снапшот. Здесь добавляем
**новый оценщик СП** в патронаж и **ветвим UI по стандарту**. Домен `CoatingSystem` и раскладку не трогаем.

Скоуп зафиксирован в обсуждении: **только металл** (Ц.1 + маппинг Ц.7), основания — углеродистая
сталь / горячий цинк / цинк+алюминий. Маркировка = `(среда=степень агрессивности, тип=условия эксплуатации)`,
**без долговечности**. Оси: пять степеней, три условия. Подтип среды наружу не выводим (вариант B).

## Секция 1. Enum'ы стандарта СП (`Domain/Compliance/Sp28/`)

**`ComplianceStandard`** (из плана 1) — добавить кейс:
```php
case SP_28 = 'SP_28';   // title() 'СП 28.13330';  description() 'СП 28.13330.2017'
```

**`SpAggressivity`** (степень агрессивности, «среда»), **четыре** значения + `rank()` (для свёртки/субсумпции) + `title()`:
```
NON_AGGRESSIVE  Неагрессивная
WEAK            Слабоагрессивная
MEDIUM          Среднеагрессивная
STRONG          Сильноагрессивная
```
Дробление слабоагрессивная-1/-2 (только для газов группы А, различает толщину I-80 vs I-120) не
моделируем — слито в `WEAK`. Требование на `(условие, WEAK)` берём **максимумом по подтипам**
(консервативно): негазовая «слабо» (соли, газы В/С/D) там и так задаёт группу II–III, что перекрывает
газы А. Следствие — тонкие системы группы I под СП не маркируются (см. развилку A′).

**`SpExploitation`** (условия эксплуатации, «тип»), три значения + `title()`:
```
INDOOR   В помещении
OUTDOOR  На открытом воздухе и под навесами
LIQUID   В жидких средах
```

Группу I–IV держим как `int 1..4` внутри оценщика (наружу не выводится, на покрытии не хранится).

## Секция 3. `Sp28Evaluator implements StandardEvaluator` (`Domain/Compliance/Sp28/`)

- `supports(ComplianceStandard $s): bool` → `$s === ComplianceStandard::SP_28`.
- `evaluate(CoatingSystem $system): Compliance[]`:
  1. Пустая система → `[]`.
  2. `column = map(system->getSubstrate())`: `STEEL_CARBON→CARBON`, `STEEL_GALVANIZED→ZINC`,
     `STEEL_METALLIZED→ZINC_AL`; иначе (бетон/нерж/алюминий/…) → `[]` (Ц.1 их не покрывает).
  3. `group = ц7group(finishLayer.base)`; `null` → `[]`. `dft = system->totalDft()`.
  4. **Свёртка подтипов**: рулбук заранее сворачивает подтипы в максимум требований на
     `(column, условие, степень)` → `(reqGroup, reqDft)`. Так «покрывает (условие, степень)» = система
     годна для любой среды этого уровня в этих условиях (консервативно).
  5. Для каждого `условие ∈ {INDOOR, OUTDOOR, LIQUID}`: найти **сильнейшую** степень, чьё требование
     выполнено (`group ≥ reqGroup` И `dft ≥ reqDft`); эмитить `Compliance(SP_28, степень, условие)`.
     Максимум одна метка на условие (сильнейшая), т.е. до трёх меток на систему.

Субсумпция: высшая группа закрывает требования низших (`≥`), сильнейшая степень покрывает слабые.

## Секция 5. UI

### 5a. Бейджи на карточке (`_list_cards.html.twig`)
Сейчас бейдж = `entry.category (+'-'+entry.durability)`, все зелёные, ISO и СП не различить. Делаем
подпись по стандарту (в шаблоне, из `entry.standard`):
- ISO → как сейчас: `C3-H`;
- СП → `среда · тип` человекочитаемо: напр. `Среднеагр. · откр. воздух`.

Различение стандартов — коротким префиксом/группировкой, без новых цветов. Точный вид — развилка C.

### 5b. Модалка предпросмотра (`coating_system_preview_controller.js#renderCompliance`)
Группировать бейджи по стандарту:
```
ISO 12944:   C3-H  C4-M
СП 28.13330: Среднеагр. · откр. воздух   Сильноагр. · в помещении
```

### 5c. Каскадный фильтр (`list.html.twig` + finder + mapper)
Сейчас значения второго/третьего уровня захардкожены под ISO (`C1..CX`, `LOW..VH`) прямо в Twig.
Ветвим по выбранному стандарту:
- ISO → Категория (C1..CX, Im1..Im3) → Долговечность (как сейчас);
- СП → Среда (пять степеней) → Тип (три условия); третьего уровня нет.

Механику (chip-facets, URL-состояние, гидрация) не трогаем — меняется только источник списка значений.
Чтобы новый стандарт не лез в Twig, значения осей отдаёт оценщик через **self-describing фасеты**
(`facets()` на `StandardEvaluator`, перебор `ComplianceStandard::cases()` × `supports()`), а
`CoatingSystemListViewFactory` прокидывает их в шаблон. Развилка D: делать `facets()` в этом плане или
временно захардкодить СП-значения в Twig рядом с ISO (быстрее, но менее чисто).

### 5d. Поиск (`CoatingSystemFinder`, `CoatingSystemListRequestMapper`, `CoatingSystemsFilter`)
- `CoatingSystemsFilter` уже несёт `standard/category/durability` строками — переиспользуем: для СП
  `category`=среда, `durability`=тип. Схему и колонки не трогаем.
- `Finder::applyCompliance()` сейчас расширяет категорию через ISO-специфичный
  `IsoCorrosivityCategory::atOrAboveInFamily()`. Для СП нужна своя «≥»-семантика: среда — по `SpAggressivity::rank()`
  (субсумпция), тип — точное совпадение. Значит ветвление ранжирования по стандарту (развилка E: общий
  интерфейс «cascade-семантика стандарта» vs `if` по стандарту в finder'е).
