# Дизайн-спека: количественный учёт СИЗ — частичное списание и дефицит выдачи

> Переигрывает Д5 (`compliance-siz-5-writeoff-acts.md`): write-off переходит с модели «переезд позиции целиком» на **количественные порции**, статус/выдача становятся **количественно-осознанными** (норма в штуках, «на руках», дефицит). Контекст `Compliance`, ветка `feat/compliance-siz-2-requirements`. Прод пуст — миграции идемпотентные, можно реформировать.

## Цель

Списывать материальные СИЗ **частями от выданного количества** и держать соответствие **по количеству норме**:
- выдано 2 пары ботинок (норма 2) → списали 1 пару (износ) → на руках 1 → система видит дефицит 1 → заводит черновик акта выдачи на **1 пару** (дефицит, не на всю норму) → оформили выдачу 1 → на руках 2 → зелёный;
- потом списали вторую → на руках 0 → дефицит 2 → черновик на 2.
- Масштаб: от 1 до 144 — без размножения фактов (количество — поле, не N записей).
- Акт списания — полноценный документ (черновик → оформлен со сканом), трассировка «из какого акта выдачи в какой акт списания».

## Модель данных

### item — `FulfillmentRecord` (факт выдачи, источник истины)
- `quantity` — выдано по этому факту (напр. 2);
- `returnedQuantity` — **суммарно списано** по этому факту (0..quantity); «на руках по факту» = `quantity − returnedQuantity`;
- `documentId` — uuid **акта выдачи** («откуда», один — выдача одна);
- `obligationKey`, `fulfilledAt`, `wearPercent`, `note`, `manualDueDate` — как есть.
- **Убираются** поля `writeOffActId`, `writeOffReason` (вводились для «переезда целиком» — не выражают частичное; переезжают на порцию).

### порция — `WriteOffItem` (сколько и почему списано в конкретном акте; дочерняя у `WriteOffAct`)
- `id` (uuid);
- `recordId` — uuid факта (какой item списываем);
- `quantity` — сколько единиц списано в **этом** акте (≤ доступного);
- `reason` — `WriteOffReason` (nullable, задаётся на странице акта);
- `writeOffAct` — many-to-one (FK), «в какой акт».
- Наименование/дату выдачи в документ/UI берём из факта (`recordId`), не снимком.
- Один факт → одна-или-несколько порций в **разных** актах (частями во времени).

### `WriteOffAct` (заголовок — как в Д5) + one-to-many `WriteOffItem`.

### `TrackedObligation` (проекция)
- Новое поле `heldQuantity` (float, денормализованное) — «на руках по позиции» = Σ(`quantity − returnedQuantity`) по фактам позиции; считается в `recompute`, нужно для дашборда (SQL-бакеты сравнивают с нормой).
- `quantity` (норма позиции) — уже есть.

## Количественная трассировка «из какого в какой»
- из какого (выдачи) = `item.documentId`;
- в какой (списания) = порции факта (`recordId`) → их `writeOffActId`; у каждой — сколько (`quantity`).

## Уровни: факт-выдача vs позиция
- **Списание адресно по факту-выдаче** (`recordId`): у позиции может быть несколько действующих выдач во времени (выдача A: 2 пары, позже выдача B: 1 пара → на руках 3 по двум фактам). Карточка показывает **действующие выдачи позиции** (факты), у каждой «на руках» = `quantity − returnedQuantity` и «Списать N». Так `recordId` точен и трассировка «из какого акта выдачи» однозначна.
- **Статус / дефицит / черновик — на уровне позиции**: `held(позиции)` = Σ по её фактам; дефицит = `норма − held`; оформление выдачи доводит held позиции до нормы.

## Поведение (инварианты — в домене)

### Списание (в корзину, без эффекта)
- «Списать N» по позиции: N ≤ **доступно** = `held − (сумма порций этого факта в открытых черновиках)`. Иначе `AppException`.
- Порция кладётся в открытый черновик акта списания по требованию (нет — создаём; инвариант: один открытый черновик-акт на требование). Причина пока null.
- Повторное «Списать» того же факта в тот же черновик → **увеличиваем `quantity` его порции** (не плодим вторую).
- Нельзя списать из недействующей карточки (нет подписанного акта выдачи) — инвариант остаётся.
- ЭФФЕКТА НЕТ: `returnedQuantity` факта не меняется, пересчёта нет.

### Откат
- Удаляем порцию целиком (частичный откат не делаем) → доступное восстанавливается. Пустой акт удаляется. Только пока акт — черновик.

### Причины
- `SetWriteOffReasons` ставит причины порциям (по id порции). Инвариант при оформлении: у всех порций причина задана, иначе `AppException`.

### Оформление акта списания (эффект — ТОЛЬКО здесь)
- Комиссия + №/дата + скан → заморозка.
- По каждой порции: `fact.returnedQuantity += порция.quantity` (с проверкой ≤ `quantity` факта).
- Пересчёт затронутых позиций → `held` уменьшается.
- Освободившийся дефицит закрывает `DraftFormationService` (см. ниже).

### Статус (худшее из количества и срока) — `ComplianceStatusResolver` + бакет-резолвер
- `held < норма` (дефицит > 0) → **красный** (недовыдано);
- `held ≥ норма`, но `nextDueAt < now` (просрочено) → красный;
- `held ≥ норма`, срок близко → жёлтый;
- иначе зелёный.
- Нематериальные (нет нормы-количества) → как сейчас, датно. held/дефицит только у материальных с `quantity`-нормой.

### Формирование черновика выдачи — `DraftFormationService`
- `hasDue` = **дефицит > 0 ИЛИ просрочено**.
- Оформление выдачи предзаполняет **дефицит** = `норма − held` (не всю норму).

### Выдача (оформление) — `assertIssuable`
- Меняется с «выдано ≥ нормы» на «**held + выдаётся ≥ норма**» по каждой материальной позиции (нельзя оставить ниже нормы). Первая выдача: held 0 → выдать ≥ норма; до-выдача: held 1, норма 2 → выдать ≥ 1.

## Открытые вопросы (решены в диалоге)
- Частичное — по количеству (порции), не per-unit (не масштабируется на 144). ✔
