# Дизайн: Compliance — переход от актов к журналу, акт списания в отдельный агрегат

> Дизайн-спека (архитектура и решения). Переосмысляет модель учёта СИЗ/обязанностей, реализованную в `compliance-siz-*.md` (акты выдачи как документы на каждую выдачу). Планы реализации по деплоям — отдельные файлы, собираются через writing-plans ПОСЛЕ утверждения этой спеки.
>
> Связано: [[project_compliance_siz_personnel]], [[project_compliance_nonmaterial_journals]], [[feedback_compliance_status_single_source]].

## 1. Зачем переделываем

Текущая реализация смоделировала **выдачу как поток актов-документов**: каждая выдача — отдельный `RequirementDocument` с циклом Черновик→Подписан, корзиной, топ-апом дефицита, сканом. После разбора с экспертами это признано промахом в модели предметной области.

В реальности для СИЗ **актов-документов на выдачу нет**. Есть **личная карточка учёта выдачи СИЗ** — один журнал на человека, куда выданное **дописывается строкой** (наименование, дата, количество, %износа). Документ-файл (.docx/.xlsx) — это **представление** поверх журнала, сделанное для печати и подписи, а не источник истины.

Суть задачи — **заполнение (ведение журнала) и мониторинг (светофор по срокам/остаткам)**, а не документооборот. Документооборотом является только **списание** — оно оформляется настоящим актом (кросс-персональным, с комиссией).

## 2. Границы

**В объёме:**
- Перевод **выдачи** (материальное) на журнальную модель: неизменяемые строки, одна карточка на человека, без актов/корзины/черновика/подписи-над-выдачей.
- Унификация **нематериального** (инструктажи) на тот же журнал фактов; документ = представление поверх фактов.
- Два **режима материальной позиции**: инвентарная (СИЗ) и расходная (ДСИЗ — крема/мыло).
- Вынос **акта списания** в самостоятельный **кросс-персональный** агрегат.
- **Ответственные/комиссия** — ссылки на `Personnel` (profileId) со снимком ФИО+должности при подписи, вместо строк.
- Вынос **проекции мониторинга** (даты/остаток/статус) из домена в read-модель.
- Мониторинг-светофор, планировщик, уведомления — поведение сохраняем, чиним протечки.

**Вне объёма (осознанно):**
- **Сканы** — паркуем. Модель проектируется скан-агностично: скан необязателен и аддитивен к карточке. Выбор «один последний / несколько / вообще отказаться» заказчик принимает с экспертами позже; ядро от него не зависит.
- **Акт выдачи как запечатанный документ-снимок** — не строим (YAGNI). Если понадобится, добавляется аддитивно: «запечатать сегмент журнала» (замок на группу строк, следующая запись открывает новый сегмент), журнал при этом не трогаем. Этот выбор склеен с выбором про сканы («несколько сканов» = запечатанные сегменты).
- Резервирование количества черновиками списания между собой — не делаем; пересечение ловим на подписи.

## 3. Ключевые решения (зафиксированы с заказчиком в диалоге)

1. **Выдача — журнал, не акты.** Одна карточка на человека (классическая «Личная карточка учёта выдачи СИЗ»): все материальные позиции человека, один шаблон. Выдача = дозапись неизменяемых строк. Строка заморожена в момент сохранения — менять нельзя; уменьшить «на руках» можно только списанием.
2. **Неизменяемость — свойство строки, а не обёртки-акта.** `held` (на руках) = Σ(выдано) − Σ(списано) по строкам. Append-only журнал + «уменьшает только списание» дают гарантию «нельзя поменять то, что на руках» без документа-акта над выдачей.
3. **Нематериальное — тоже журнал.** Каждое прохождение инструктажа/курса = неизменяемая строка с `InstructionDetails`. Документ (.docx, шаблон на требовании — пожарный/ОТ) = представление поверх фактов, рендерится по требованию. Печатать «только что положено пройти» — настройка проектора, на модель данных не влияет. Акта-над-прохождением нет.
4. **Материальная позиция имеет два типа (флаг на позиции требования; в UI — «Тип»):**
   - **Инвентарь** (обычные СИЗ): статус по остатку (`held` vs норма) И по дате; **подлежит списанию**; `held` долговечный (уменьшается только списанием).
   - **Расходник** (ДСИЗ: крема, мыло): статус считается **точно так же, как у инвентаря** — и по количеству (недовыдал → красный), и по дате. Единственное отличие — **не участвует в акте списания**. Но его `held` не копится: выданный расходник «сгорает» к концу своего срока (Вариант B, см. §4.6) → честное «на руках». Количество — **есть** (структурный `Quantity`, напр. 1200 мл; НИКОГДА не в названии).
   - (Ранее тут было «расходник по дате, остаток игнорируется» — ОТМЕНЕНО заказчиком: расходник краснеет и по количеству, и по дате; отличие только в списании.)
5. **Списание — самостоятельный кросс-персональный агрегат `WriteOffAct`.** В одном акте списываются позиции у РАЗНЫХ людей (у Иванова — одно, у Петрова — другое). Строка акта = `{profileId, recordId, количество, причина}`. **Частичное по количеству**: один факт выдачи можно списывать частями в разных актах во времени (аккумулятор списанного). Только инвентарные материальные позиции попадают в списание; расходные и нематериальные — никогда.
6. **Применение списания — синхронно, одной транзакцией (Вариант A).** При подписи акт грузит затронутые `ProfileCompliance`, применяет уменьшение к их строкам журнала, пересчитывает проекцию, сохраняет всё одной транзакцией. Строгая согласованность, нет окна «подписано, но held не уменьшился». Черновик ничего не резервирует; «хватает ли на руках» проверяется в момент подписи. Мультиагрегатная транзакция допустима (единый flush Doctrine, низкая конкурентность бэк-офиса).
7. **Ответственные/комиссия → profileId.** Ответственный на выдаче, представитель и члены комиссии на списании — ссылки на `Personnel\Profile`. Подписанный акт — юр.документ: ФИО+должность **замораживаются снимком в момент подписи** (голый profileId показал бы новые данные после смены должности).
8. **Проекция мониторинга — вне домена.** Даты (`lastFulfilledAt`, `nextDueAt`), `held`, бакет — НЕ хранятся в агрегате. Их материализует **проектор в Application/Infrastructure** в индексированную read-таблицу для дашборда/планировщика. Статус считает **единый резолвер** (`ComplianceStatusResolver`, `DUE_SOON_DAYS=60`), ветвясь по режиму обязанности.

## 4. Карта агрегатов

### 4.1 `Requirement` (норма) — правки точечные

Остаётся как есть (тип `Material`/`NonMaterial` неизменяем, позиции полиморфны, шаблон+`journalKind` на требовании). Изменения:
- На `MaterialItem` — **тип** (enum `MaterialMode`: `inventoried`/`consumable`, в UI «Тип: инвентарь/расходник»). Светофор у обоих одинаков (кол-во+дата); тип управляет только применимостью списания (инвентарь — да, расходник — нет) и сгоранием `held` у расходника (§4.6). У `NonMaterialItem` типа нет.
- **Стабильный id позиции.** Каждому `RequirementItem` — персистентный `id` (uuid). Факты журнала ссылаются на `requirementId + itemId`, а НЕ на строковый ключ `requirementId|label`. Это чинит хрупкость: переименование позиции (регистр/пробелы) больше не рвёт связь факта с нормой.

### 4.2 `ProfileCompliance` (учёт на человека) — похудевший

Держит ТОЛЬКО источники истины:
- **Журнал фактов** `FulfillmentRecord[]` — неизменяемые строки выдачи/прохождения. Поля: `id`, ссылка на обязанность (`requirementId+itemId` или personalObligationId), `fulfilledAt`, `?Quantity issuedQuantity`, `?float wearPercent`, `?InstructionDetails`, `?manualDueDate`, `float writtenOffQuantity` (аккумулятор, растёт при подписи акта списания, ≤ выданного), снимок `writeOffApplicable` (из режима позиции на момент выдачи — чтобы списание не переджойнивало норму), `?responsibleProfileId`+снимок ФИО.
- **Персональные отклонения** — добавленные вне нормы обязанности (`origin=personal`, со своим id/типом/cadence) и исключения (`excludedObligationIds`).

Что УХОДИТ из агрегата: `RequirementDocument` (акты выдачи), корзина/черновик/топ-ап/подпись-над-выдачей, вшитый `WriteOffAct`/`WriteOffItem`, материализованная проекция `TrackedObligation` (даты/held/статус/active), `worstStatus()` (read-concern), прямой путь `recordFulfillment` (чёрный ход).

Публичные операции (примерно): `recordIssuance(IssuanceLine ...$lines)` (дозапись неизменяемых строк — ЕДИНСТВЕННЫЙ путь факта), `recordInstruction(...)` (нематериальное, с доменной проверкой полноты полей), `applyWriteOff(recordId, qty)` (вызывается из подписи акта, инвариант qty ≤ held факта), `addPersonalObligation`/`excludeObligation`, `heldOfRecord(recordId)`. Инварианты (held-арифметика, количество ≤ нормы при выдаче, полнота `InstructionDetails`, qty ≤ held при списании) — в домене.

### 4.3 `WriteOffAct` (акт списания) — новый самостоятельный агрегат, кросс-персональный

Корень. Поля: `id`, `WriteOffActLine[]` (`{profileId, recordId, label-снимок, quantity, WriteOffReason}`), `DocumentStatus` (Draft/Signed), реквизиты (`actNumber`, `actDate`, `orderNumber`, `orderDate`), **представитель** (`profileId` + снимок позиции/ФИО), **комиссия** (`profileId[]` + снимки), `?scanFileId`, `signedAt`, `version`.

Жизненный цикл:
- `Draft` — общая корзина: набираем строки у разных людей, правим количество/причину/реквизиты. Ничего не применяет.
- `sign(...)` — инвариант: причины у всех строк заполнены, комиссия непуста; замораживает снимки ФИО комиссии/представителя. Применение к журналам — синхронно в той же транзакции (Вариант A): по каждому `profileId` грузим `ProfileCompliance`, зовём `applyWriteOff(recordId, qty)`, пересчитываем проекцию, сохраняем. Проверка held ≥ qty — здесь.

Инвариант: строка ссылается только на факт **инвентарной материальной** обязанности (по снимку `writeOffApplicable` на факте) с `held ≥ qty`.

### 4.4 Read-модель мониторинга (вне домена)

Проектор (Application) материализует per (profile × обязанность) строку в индексированную таблицу `compliance_obligation_projection` (Infrastructure): `label`, `type`, `mode`, `cadence`, `normQuantity`, `lastFulfilledAt`, `nextDueAt`, `heldQuantity`, `bucket`. Источник — текущие `Requirement` + персональные отклонения + факты журнала. Пересобирается по событиям (норма/профиль изменились, акт списания подписан, факт записан). Дашборд и планировщик читают эту таблицу (дёшево, по индексу `nextDueAt`/`bucket`).

**Статус — единый резолвер, БЕЗ ветвления по типу материала:**
- Материальное (и инвентарь, и расходник): нет факта или `held < норма` → Missing; иначе по датам (`nextDueAt` < now → Overdue; ≤ `DUE_SOON_DAYS` → Soon; иначе Ok). Разница инвентарь/расходник только в том, ЧТО такое `held`: у инвентаря — долговечный остаток (Σвыдано−Σсписано), у расходника — «живой» (невыдохшие выдачи, §4.6).
- Нематериальное: `norm=null` → held-гейт не применяется, статус по дате.

### 4.5 Норма меняется: контроль по текущей норме, списание по факту (зафиксировано с заказчиком)

Норму правят во времени. Правила:
- **Мониторинг — по ТЕКУЩЕЙ норме.** Обязанность (что контролируем) = позиции текущей нормы должности + персональные добавки. Статус инвентарной позиции = `held` vs **текущая** норма. Пример: было 2 пары ботинок/год, выдали 2, норму снизили до 1 — контролируем «≥1 пара/год»; `held=2 ≥ 1` → Ok, лишняя пара не краснит.
- **Позиция убрана из нормы → перестаёт контролироваться,** но её удерживаемые факты остаются (физически на руках). Они НЕ висят как просроченные — чинит баг «удалённая из нормы лезет в просрочку/в черновик выдачи».
- **Списание — по ФАКТУ (held), не по норме.** Списать можно до `held` (хоть всё выданное), независимо от текущей нормы. Поэтому `writeOffApplicable` — снимок на факте: норма позиции может уже не существовать, а списывать удержанное надо.
- Следствие — **две проекции над журналом**: (1) *контролируемые обязанности* (текущая норма + персональные → дашборд/светофор/алерты); (2) *удерживаемый инвентарь* (факты с `held>0` и `writeOffApplicable` → экран набора акта списания). Факт может быть в инвентаре, но вне контроля (убран из нормы).

### 4.6 Потребление расходника — честный «тающий» held (Вариант B, ОТДЕЛЬНЫЙ деплой)

Заказчик (DDD — моделируем бизнес): расходник потребляется к концу срока. Правила (зафиксированы):
- Каждая выдача расходника «живёт» ровно один свой cadence-период **от даты выдачи** (катящийся срок: выдал 15-го, период месяц → истекает 15-го след. месяца). В конце срока **сгорает целиком** (бинарно, не постепенно).
- `effectiveHeld(расходник, now)` = Σ количество невыдохших выдач (где `fulfilledAt + cadence > now`). Светофор = `effectiveHeld < норма` → красный (истечение «встроено» в срок, отдельный date-гейт не нужен).
- Пример: мыло 2 куска/мес; выдали 1 → effectiveHeld 1 < 2 → красный; выдали 2 → зелёный; через месяц обе выдачи истекли → effectiveHeld 0 < 2 → красный.

**Почему отдельный деплой, а не часть D1:** `effectiveHeld` зависит от `now` и убывает БЕЗ события (просто от хода времени) — его нельзя хранить статичным числом в проекции, надо считать на чтении из самих выдач (дата+кол-во+cadence). Это цепляется за вынос проекции из домена (D4). Пока B не сделан, расходник по статусу = инвентарь (held долговечный, см. §4.4) — светофор верный, но отображаемое «на руках» у расходника копится (косметически неверно). B чинит именно честность «на руках».

**Статус D1:** `Task 7` (расходник «по дате», held игнор) был ошибкой ранней формулировки — **откатан**. D1 = расходник считается как инвентарь; флаг «Тип» заложен (роль — списание + будущее B).

## 5. Потоки

1. **Выдача СИЗ/расходника.** Экран карточки человека → «Выдать» → открывается **форма** (не черновик-документ), предзаполненная позициями **текущей нормы** человека (по всем его требованиям), количество = **дефицит**, вычисляемый ПРИ ОТКРЫТИИ и нигде не хранимый: инвентарное `норма − held`; расходное — норма при наступлении срока (по дате, остаток не вычитаем). Количество переопределяемо (замена/досрочная выдача); опц. блок «добавить позицию вне нормы» (персональная). В форму попадают только контролируемые позиции — убранные из нормы, но удерживаемые НЕ предлагаются к выдаче (их путь — списание; чинит баг «удалённое из нормы лезет в выдачу»). Сохранение = `recordIssuance` — строки пишутся **прямо в журнал**, сразу неизменяемы; возврат на карточку с пересчитанными held/светофором. **Черновика/топ-апа нет** — дефицит был начальным состоянием формы, а не сохранённой корзиной (в старой модели `topUpDraftFromNorm` копил лимбо — см. §8, 24 подвисших черновика на проде). Печать карточки — проектор поверх журнала (норма + лог), шаблон требования/дефолт. Скан (если оставим) — опционально к карточке, потом.
2. **Прохождение инструктажа.** Экран карточки → «Отметить прохождение»: дата + поля `InstructionDetails` по схеме `JournalKind`. Домен проверяет полноту обязательных полей (инвариант на записи). Печать журнала — проектор поверх фактов, шаблон требования.
3. **Списание (кросс-персональное).** Отдельный раздел «Акты списания»: создать акт → набрать в корзину удерживаемые позиции у разных людей (поиск по человеку/позиции, показываем `held`), количество+причина по строке, комиссия/представитель (`typeahead` по profiles), реквизиты. «Оформить» → подпись → применение к журналам + заморозка снимков. Печать акта (.docx) — проектор. Скан — опционально.
4. **Мониторинг.** Дашборд-светофор (по людям/отделам/требованиям), 4 бакета, фильтры в URL, превью человека. Читает read-проекцию. Планировщик (06:00 МСК) сканирует проекцию по `nextDueAt`, шлёт дайджест ответственному/админам. Поведение сохраняем.

## 6. Архитектурные ограничения (пять промахов → жёсткие правила)

1. **Расщепить god-агрегат.** Акт списания — свой агрегат; `ProfileCompliance` = журнал фактов + персональные отклонения. Без документооборота внутри.
2. **Не перетяжелять.** Никаких актов/корзины/топ-апа над выдачей; документооборот только в списании.
3. **Проекцию — вне домена** (read-модель, проектор, единый резолвер). Домен не знает про дашборд.
4. **Один путь фиксации факта** — запись в журнал (`recordIssuance`/`recordInstruction`). Прямой `recordFulfillment`-чёрный ход убрать.
5. **Инварианты — в домене** (полнота полей инструктажа, held-арифметика, qty ≤ held, количество ≤ нормы). Не в хендлерах/мапперах.

## 7. Чистки по ходу (из аудита текущего кода — делаем там, где касаемся)

- `IssueAction` ~220 строк read-model в контроллере → в view-builder/query.
- Пороговые сравнения (`held</=/>` норма, `1e-9`) в Infrastructure дублируют резолвер → в домен/резолвер.
- Форматирование числа (4 копии) и сборка ФИО (~8 копий) → общий форматтер/VO (ФИО — `FullName::short()` у Personnel уже есть, переиспользовать через DTO).
- 6-аргументный вызов `bucketFor(...)` в 4 местах → метод на обязанности read-модели.
- Контроллеры, лезущие в репозиторий в обход query-шины для чтения → через query.
- `ComplianceAccessControl::canManage()/isManager()` дубль и `canView()=true` → прибрать.
- Антифлуд планировщика (шлёт повтор ежедневно) — известная дыра, решить при переносе проекции.

## 8. Данные и миграции

- **Прод НЕ пуст** (сверено 2026-10-14 на подтянутой прод-БД): `compliance_requirement` 3, `compliance_requirement_document` 26 (**2 signed + 24 formed/черновики**), `compliance_fulfillment_record` 126 (**все привязаны к документам**, прямых фактов нет), `compliance_tracked_obligation` 124, `compliance_write_off_act` 3 / `compliance_write_off_item` 8, `personnel_profile` 11. Значит миграция — с **реальным бэкфиллом**, не «схема с нуля».
- Переход актов→журнал (точная ревизия на этапе планирования): факты 2 подписанных актов → неизменяемые строки журнала (`document_id` отвязать). **24 формед-черновика** = незавершённые корзины (валидирует редизайн: церемония копила лимбо) — решить **на данных**: промотировать их факты в журнал ИЛИ отбросить как недооформленные (вероятно, с заказчиком поштучно/оптом).
- `write_off` (3 акта + 8 позиций) из `profile_compliance` → перенести в самостоятельный `WriteOffAct` (кросс-персон), сохранив ссылки на factId и снимки.
- `tracked_obligation` (124) — **не** переносить вручную, пересобрать проектором из текущей нормы + фактов.
- Новые/изменённые таблицы: `requirement_item` (id позиции, режим), `compliance_write_off_act` (кросс-персон, снимки комиссии/представителя через profileId), `compliance_obligation_projection` (read-модель), правки `compliance_fulfillment_record` (itemId-ссылка, снимок writeOffApplicable, responsibleProfileId+снимок). Точный состав — в планах.

## 9. Декомпозиция на деплои (ориентир; детальные планы — через writing-plans)

Каждый деплой самодостаточен и отгружаем. Предварительная последовательность (уточним при планировании):
- **Д1. Режим позиции + ветвление статуса.** Флаг инвентарная/расходная на `MaterialItem`, резолвер ветвится (расходное — по дате). Стабильный id позиции. Аддитивно, низкий риск.
- **Д2. Журнальная выдача.** Снос актов выдачи/корзины/топ-апа/подписи; `recordIssuance` неизменяемых строк; карточка-проектор поверх журнала; held из строк.
- **Д3. Унификация нематериального на журнал.** Прохождение = строка факта; инвариант полноты полей в домен; документ-проектор поверх фактов.
- **Д4. Вынос проекции мониторинга из домена** в read-таблицу + проектор + единый резолвер; дашборд/планировщик читают её. (Может слиться с Д2.)
- **Д5. `WriteOffAct` — отдельный кросс-персональный агрегат** (Вариант A), экран набора по разным людям, применение при подписи, миграция.
- **Д6. Ответственные/комиссия → profileId + снимок.** Деликатно: `Commission`-VO переиспользуется в Reports (`report/fill`) — не сломать отчёты; отдельный аккуратный деплой.

Порядок/слияние деплоев — решение этапа writing-plans.

## 10. Открытые/отложенные вопросы

- **Сканы**: один последний / несколько / отказаться — решает заказчик с экспертами. Ядро скан-агностично. «Несколько сканов» ⇒ концепция «запечатанного сегмента/акта выдачи», которую тогда и достроим.
- **Акт выдачи как документ-снимок** — отложен (YAGNI), аддитивен.
- **Режим позиции** — enum (`inventoried`/`consumable`) против bool `writeOffApplicable`: решить при Д1 (enum расширяемее).
- Точная граница `Commission`-VO между Compliance и Reports при Д6.

## 11. Тестирование

- Домен: юнит-тесты инвариантов (неизменяемость строки, held-арифметика, qty ≤ held, количество ≤ нормы, полнота `InstructionDetails`, кросс-персон подпись акта) — зеркалят `src/`.
- Application-хендлеры: функциональные с реальной БД (выдача, прохождение, списание у двух людей одним актом, пересчёт проекции по событиям).
- Резолвер статуса: таблица кейсов по обоим режимам (остаток vs дата).
- Mapper-ы: round-trip формы.
- `./run check` зелёный на каждом шаге (style/phpstan/unit/functional), не только phpunit.
