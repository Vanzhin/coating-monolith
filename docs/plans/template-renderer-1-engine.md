# Универсальный движок заполнения шаблонов документов — Деплой 1 (stateless-движок)

Статус: **РЕАЛИЗОВАН 2026-09-18** (ветка `feat/template-renderer` от `main`) — 52 теста зелёные, phpstan/cs-fixer чисто, `lint:container` ок; НЕ закоммичен.
Тип: architectural (новая подсистема в `Shared`).

Ревью (2026-09-18, high): 6 находок, 3 CONFIRMED исправлены — (1) плейсхолдеры колонтитулов теперь обнаруживаются (`parse` берёт `getVariables()` тела+колонтитулов); (2) xlsx `setValueExplicit` STRING (значения с `=`/числами не становятся формулой); (3) глобальные макро-скобки восстанавливаются в `__destruct`. Остальные 3 (повторный load за render — efficiency; дубль `{{x}}`/`{{x?}}` — порядок; незакрытый блок → обязательное поле) приняты как незначимые/бэклог. Драйверы+фасад перенесены в `Shared/Infrastructure/Service/`.
Соседний план: Деплой 2 «Управление шаблонами» (`docs/plans/template-renderer-2-management.md`) — **ещё не написан**, здесь только шов к нему.

## 1. Цель

Один универсальный сервис «шаблон + данные → документ». На входе — заранее подготовленный файл-шаблон
с неизменяемым текстом и плейсхолдерами `{{переменная}}`, и конфиг «ключ → значение». Сервис:

1. вытаскивает из шаблона список требуемых переменных;
2. сверяет конфиг с шаблоном и говорит, чего не хватает (до генерации);
3. заполняет и отдаёт готовый файл **в формате шаблона**.

Сервис не знает про конкретный шаблон: шаблон можно подменить — движок заново сверит переменные и заполнит.
Домен (покрытия и пр.) про движок ничего не знает.

**Форматы: Word (`.docx`) и Excel (`.xlsx`)** — через единый интерфейс, конкретный класс-драйвер сам ищет и
подставляет в своём формате.

Первый потребитель: пользователь заполняет отчёт (акт) в приложении → на выходе Word.
Будущий потребитель: регламент на окраску для систем покрытий (тот же движок, другой шаблон).

## 2. Границы

Сервис делает **только** это:
- по шаблону вернуть список переменных с пометкой обязательная/опциональная;
- сверить конфиг с шаблоном → сказать, чего не хватает;
- заполнить → отдать готовый файл в формате шаблона.

Сервис **не** делает:
- **конвертацию форматов** (docx→PDF и пр.) — не его задача.
- **хранение/загрузку/реестр шаблонов** — это Деплой 2 (B). В Деплое 1 шаблон приезжает как путь к файлу.
- **построение формы ввода, метаданные переменных** (лейблы, типы) — забота потребителя. Движку хватает имён
  переменных из самого шаблона.
- **форматирование значений** (даты, числа, локали) — вызывающий передаёт готовую строку.
- **оформление текста** (жирный/курсив/цвет/размер/шрифт) — берётся из самого шаблона (стилизованный
  `{{placeholder}}`), в конфиге его нет.
- **repeat** (повтор строк/колонок переменной длины) — не в Деплое 1 (см. §7).

Принцип: «минимум логики» — разность множеств (что требует шаблон vs что дали), проверка существования
файлов-картинок, механическая подстановка и удаление опциональных блоков по наличию данных.

## 3. Архитектура

Structure 1 (согласовано): stateless-сервис в `Shared/`, порт + драйверы по формату + фасад-диспетчер.
Домена почти нет — механика, не бизнес-правило. Любой контекст (акт, будущий регламент) вызывает фасад.

### Единый контракт

```php
interface TemplateRenderer {
    public function supports(TemplateFile $template): bool;            // по формату
    public function variables(TemplateFile $template): array;          // list<TemplateVariable> {name, optional}
    public function validate(TemplateFile $template, RenderData $data): ValidationResult;
    public function render(TemplateFile $template, RenderData $data): RenderedDocument;
}
```

- **`variables`** — список плейсхолдеров шаблона, каждый с флагом `optional` (см. §6). Из него потребитель строит
  форму и знает, что обязательно, а что нет.
- **`validate`** — сверка конфига с шаблоном, возвращает `ValidationResult`, **не кидает**. Для UX «покажи,
  чего не хватает, до генерации».
- **`render`** — заполняет, отдаёт готовый файл. **Строгий**: внутри зовёт `validate`, при невалидных данных
  кидает `AppException` (см. §6).

### Драйверы (конкретные классы, каждый сам ищет и меняет в своём формате)

- **`DocxTemplateRenderer`** — на PhpWord (`TemplateProcessor`). Возможности: **text + image + optional block**.
- **`XlsxTemplateRenderer`** — на PhpSpreadsheet, плейсхолдеры `{{key}}` прямо в ячейках. Возможности: **text**.

### Фасад-диспетчер

`TemplateRendering` — универсальная точка входа, которой всё равно какой шаблон. По формату `TemplateFile`
выбирает драйвер (Symfony tagged-iterator + `supports()`), делегирует `requiredVariables/validate/render`.
Формат не поддержан ни одним драйвером → `AppException`. Потребитель передаёт `TemplateFile` и про формат не думает.

### Расхождение возможностей форматов (зафиксировано явно)

| Возможность | docx (PhpWord) | xlsx (PhpSpreadsheet) |
|---|---|---|
| text (`{{key}}`) | да | да |
| image | да | позже (Drawing по якорю-ячейке) |
| **optional block** | да (`deleteBlock`) | **нет родного понятия** (спрятать регион = удалять строки/колонки — другой механизм) |
| валидация missing/unused | да | да |

Контракт (три метода) и модель данных — **общие**. `optional block` — возможность docx-драйвера, а не
обязательная часть кросс-форматного контракта: как драйвер трактует блоки внутри — его дело. Понадобится
условность в xlsx — придумаем xlsx-механизм тогда, контракт не сломается.

### Отклонённые варианты

- Новый bounded context сейчас — преждевременно (вырастет с B, см. §11).
- Обобщить `Proposals` xlsx-пайплайн (label-matching + PDF) — потащит проповые понятия; отклонено. Наш
  `XlsxTemplateRenderer` — на `{{}}`, единообразно с docx. Существующий Proposals-xlsx **не трогаем**;
  возможная миграция — будущее, вне scope.

## 4. Публичный API — пример использования (потребитель — флоу акта)

```php
$template = new TemplateFile($pathToDocx); // формат определится из расширения
$data = new RenderData([
    'object'          => new TextValue('Балка Б2-3'),
    'l1_material'     => new TextValue('Литамастик 290 Норд'),
    'l1_comp_a_batch' => new TextValue('LO00-4126.2.1 от 01.06.2026'),
    'l1_comp_b_batch' => new TextValue('LO00-4059.2.1 от 22.05.2026'), // двухкомпонентный
    'photo_1'         => new ImageValue('/abs/path/photo1.jpg', width: 400),
]);

$result = $rendering->validate($template, $data);
if (!$result->isValid()) {
    // блокеры: $result->missing / unresolvedImages (обязательных) / invalidBlocks
}
// $result->skipped — пропущенные опциональные (в т.ч. фото), не блокируют, но можно показать

$doc = $rendering->render($template, $data); // AppException, если невалидно
// $doc->extension() === 'docx' — сохранить / отдать / передать на конвертацию
```

Для однокомпонентного материала домен просто **не кладёт** `l1_comp_b_batch` → строка «Комп. Б …» в документе
удаляется целиком (см. §6, optional block).

## 5. Модель данных (общая для обоих форматов)

Все VO — `final readonly`.

**`TemplateFile`** — путь к файлу-шаблону + формат.
Конструктор валидирует **форму**: путь не пуст + расширение из поддерживаемых (`.docx`/`.xlsx`); из расширения
выводит `format(): TemplateFormat`. Существование/читаемость файла проверяет драйвер в момент `validate`/`render`
(VO в проекте чистые, без I/O в конструкторе — как `Link` валидирует форму URL). Битый/отсутствующий файл →
`AppException` из драйвера с техническим `$log`.

**`TemplateFormat`** — `enum { Docx; Xlsx; }`, из расширения.

**`RenderData`** — обёртка над `array<string, TemplateValue>` (ключ = имя переменной, уникальная строка).
Методы: `variableNames(): list<string>`, `get(string $name): ?TemplateValue`, `has(string $name): bool`.
**Плоский** presence-driven конфиг — часть ключей опциональна (относится к блокам, см. §6).

**`TemplateValue`** — маркер-interface. Sealed-набор:
- **`TextValue`** — `__construct(string $value)`. Строго `string`; форматирование — забота вызывающего.
- **`ImageValue`** — `__construct(string $path, ?int $width = null, ?int $height = null)`. Путь к картинке +
  опц. размер (px). Явный размер уважается как есть. Размер не задан → **ширина клампится до дефолта
  (~600px, если натуральная больше)**, пропорции сохраняются, чтобы фото не разносило вёрстку (см. §6).
  (docx v1; xlsx-image — позже.)

`render` ветвится по типу (`match`/`instanceof`). Никаких строковых `kind`.

**`TemplateVariable`** — дескриптор плейсхолдера из интроспекции: `{ name: string, optional: bool }`. `optional`
= в шаблоне помечен `{{name?}}` **или** сидит внутри опционального блока. Маркеры блоков (`opt_x`, `/opt_x`) — не
переменные, в список не попадают.

**`ValidationResult`** — данные, не исключение:
- `missing: list<string>` — **обязательные** плейсхолдеры без значения в `data` (блокирует);
- `unresolvedImages: list<string>` — **обязательные** image-плейсхолдеры, чей файл не найден/не читается (блокирует);
- `invalidBlocks: list<string>` — опциональные блоки с **частично** заполненными полями (блокирует; docx, см. §6);
- `skipped: list<string>` — **опциональные** плейсхолдеры, пропущенные (нет данных или у опц. картинки битый файл) —
  очищаются, **не блокируют**, предупреждение;
- `unused: list<string>` — ключи `data`, которых нет в шаблоне (не блокирует, инфо);
- `isValid(): bool` — `true`, когда пусты `missing`, `unresolvedImages`, `invalidBlocks` (`skipped`/`unused` не блокируют).

Человекочитаемые тексты строит потребитель-форма; сервис отдаёт факты.

**`RenderedDocument`** — готовый файл + метаданные: поток/байты, расширение (`docx`/`xlsx`), mime. Хранить/скачать/
отдать на конвертацию решает вызывающий.

## 6. Поведение

**Синтаксис `{{}}`.** docx: адаптер переопределяет макро-скобки PhpWord на `{{`/`}}`
(`TemplateProcessor::$macroOpeningChars`/`$macroClosingChars`). xlsx: `{{key}}` в тексте ячеек. Соглашение для
авторов: имена переменных — латиница `snake_case`.

**Обязательные и опциональные плейсхолдеры.** Метка опциональности — суффикс `?`: `{{name}}` — обязательный,
`{{name?}}` — опциональный. `?` — часть метки, в имя переменной не входит (`{{photo_1?}}` → ключ `photo_1`).
`variables()` возвращает каждый плейсхолдер с флагом `optional`. Опциональны также плейсхолдеры внутри
опционального блока (по membership).

**Что «не хватает»:**
- `required` = обязательные плейсхолдеры (без `?`, вне опц. блоков; xlsx: все без `?`).
- `missing` = `required` минус ключи `RenderData` (блокирует).
- `skipped` = опциональные плейсхолдеры без данных (или опц. картинка с битым файлом) — очищаются, **не блокируют**.
- `unused` = ключи `RenderData` минус все плейсхолдеры шаблона (инфо, не блок).
- **Пустая строка — валидное значение, не `missing`.** `missing` = ключа вообще нет; `TextValue('')` =
  осознанно пустое поле.

**Optional block (только docx).** Пара маркеров `{{opt_name}} … {{/opt_name}}` вокруг региона (строки/ячейки/
абзаца). Имя — просто метка для связки открытие/закрытие, **не поле-значение**.
- **Membership:** переменные ВНУТРИ блока — необязательные; ВНЕ блоков — обязательные. `requiredVariables()`
  возвращает только внеблочные.
- **Keep/delete (presence-driven):** пришли данные для полей блока → блок остаётся и заполняется (`cloneBlock`
  с 1); не пришли → блок удаляется целиком (`deleteBlock`). Решает домен: положил данные или нет.
- **All-or-none:** в блоке несколько полей — либо все пришли, либо ни одного. Частично → `invalidBlocks`
  (невалидно), чтобы в оставленном блоке не торчало незаполненное `{{...}}`.
- **Нюанс расстановки:** чтобы удалялась вся строка/абзац (а не осталась пустая), маркеры размещаются так, чтобы
  абзац/ячейка целиком попали в блок. Решается на этапе кода, логику не меняет.

Пример (ячейка «№ партии» слоя 1, шаблон):
```
Комп. А № партии {{l1_comp_a_batch}}
{{opt_l1_comp_b}}Комп. Б № партии {{l1_comp_b_batch}}{{/opt_l1_comp_b}}
```
Двухкомпонентный (домен положил `l1_comp_b_batch`) → обе строки. Однокомпонентный (не положил) → строки
«Комп. Б …» нет вовсе, ни прочерка, ни пустой строки.

**Строгий `render`.** Внутри зовёт `validate`; `!isValid()` → `AppException` со списком недостающего в контексте
(→ HTTP 422 → форма покажет ошибку). Гарантия: невозможно сгенерить документ с торчащими `{{...}}`, битой
картинкой **обязательного** поля или полу-заполненным блоком. Опциональные (`?`) отсутствия не блокируют —
плейсхолдер очищается, попадает в `skipped`, генерация идёт. Фронт/форма никогда не решают «можно ли генерить».

**Картинки (docx v1).** `ImageValue` → `setImageValue(name, ['path'=>…, 'width'=>…, 'height'=>…, 'ratio'=>true])`.
Файл не найден/не читается: у **опционального** плейсхолдера (`{{photo?}}`) → `skipped`, картинка пропускается,
`render` **не падает**; у **обязательного** → `unresolvedImages`, `render` падает. (В отчёте фото метят `?`, поэтому
они не стопят процесс — ровно требование «из-за фоток нельзя останавливать генерацию».)
**Дефолтный кламп ширины:** если размер в `ImageValue` не задан, драйвер ставит `width = min(натуральная, ~600px)`
c `ratio=true` (именованная константа-дефолт), чтобы большое фото не ломало вёрстку. Явный `width`/`height` —
без клампа. Это про раскладку, не про вес файла: PhpWord встраивает **оригинальные байты** картинки, кламп их не
уменьшает. **Настоящий лимит веса/разрешения — на загрузке у потребителя** (Symfony `Image`-констрейнт:
`maxSize`/`maxWidth`/`maxHeight`), не в движке.

**Statelessness / ошибки.** Каждый `render` строит свежий процессор из файла-шаблона, шаблон не мутируется, на
выходе новый поток/байты. Между вызовами состояния нет. Битый/непарсящийся/отсутствующий файл → `AppException`
с техническим `$log`. Кириллица в значениях — ок (UTF-8).

## 7. Про repeat и слои (решение)

Таблица слоёв в реальных актах **транспонирована**: слои — колонки, параметры — строки. Родной повтор PhpWord
(`cloneRow`) повторяет строки, не колонки; повтора колонок из коробки нет.

**Решение (согласовано):** вместо повтора — **отдельные шаблоны на 1 / 2 / 3 / 4 слоя** (больше в системах не
бывает). Тогда таблица слоёв — плоские поля (`{{l1_…}} {{l2_…}} {{l3_…}}`), и **repeat в Деплое 1 не нужен вовсе**.

repeat (`cloneRow`/`cloneBlock` + списочная модель данных) остаётся возможным будущим инкрементом, если появятся
переменные списки, которые не хочется фиксировать числом (комиссия, перечень замечаний). Не в этом scope.

## 8. Зависимости и регистрация

- Новая composer-зависимость: `phpoffice/phpword` (^1) — под docx. `phpoffice/phpspreadsheet` уже в проекте.
- Драйверы и фасад — обычные Symfony-сервисы (autowire). Драйверы собираются в фасад через tagged-iterator
  (тег/интерфейс `TemplateRenderer`).
- Макро-скобки docx задаются в драйвере.

## 9. Тесты

Зеркалят `src/`.

**Юнит-тесты VO** (`tests/Unit/Shared/Templating/...`):
- `TemplateFile`: ок для `.docx` и `.xlsx` (+ верный `format()`); `AppException` на неизвестное расширение;
  `AppException` на пустой путь.
- `TextValue` / `ImageValue`: конструирование, геттеры.
- `RenderData`: `variableNames()` / `get()` / `has()`.
- `ValidationResult::isValid()` — матрица: пусто → valid; только `unused` → valid; `missing`/`unresolvedImages`/
  `invalidBlocks` (любое) → invalid.

**Интеграция `DocxTemplateRenderer`** (реальный PhpWord + фикстуры, без БД):
- `variables()` — флаг `optional`: `{{x}}` → false, `{{x?}}` → true, внутриблочные → true; маркеры блоков исключены.
- `validate()` — раскладывает `missing` / `skipped` / `unused` / `unresolvedImages` / `invalidBlocks`.
- `render()` happy-path — переоткрыть выход, `getVariables()` == `[]` + искомое значение в `word/document.xml`.
- `render()` строгий — `AppException` при `missing`, при битом файле **обязательной** картинки, при частичном блоке.
- опциональный плейсхолдер `{{x?}}` без данных → `skipped`, `render` не падает, в выходе нет `{{x?}}`.
- опциональная картинка с битым файлом → `skipped`, `render` не падает.
- optional block — фикстура с блоком: двухкомпонентный (данные есть) → строка «Комп. Б» присутствует;
  однокомпонентный (данных нет) → строки нет.
- image — в выходном `.docx` появляется `word/media/*`.

**Интеграция `XlsxTemplateRenderer`** (реальный PhpSpreadsheet + фикстуры):
- `variables()` — плейсхолдеры из ячеек с флагом `optional` (`{{x?}}` → true).
- `render()` — заполняет ячейки; переоткрыть, не осталось `{{}}`; значение на месте.
- `render()` строгий — `AppException` при `missing`; опциональный `{{x?}}` без данных → `skipped`, очищается.

**Диспетчер `TemplateRendering`:**
- выбирает docx- vs xlsx-драйвер по расширению; неизвестный формат → `AppException`.

**Фикстуры:** крошечные `.docx` (текст; с картинкой; с опциональным блоком) и `.xlsx` (текст) в
`tests/.../Resources/` + тест-png. Коммитим в репо.

## 11. Лог решений (закрыто в брейншторме)

- Данные — плоский конфиг «ключ → значение», объект вместо массива. (Q1: скаляры.)
- Конвертация форматов — не задача сервиса.
- Управление шаблонами — Деплой 2 (C). Сейчас stateless-движок, шаблон как путь.
- Тип «текст vs картинка» — типизированное значение (`TextValue`/`ImageValue`), не эвристика/имя. (Q4: A.)
- Оформление текста — из шаблона, не из конфига. `TextStyle` не заводим.
- `render` строгий; пустая строка ≠ missing.
- **Мульти-формат: порт `TemplateRenderer` + драйверы `DocxTemplateRenderer` (PhpWord) / `XlsxTemplateRenderer`
  (PhpSpreadsheet) + фасад-диспетчер по формату.**
- **Optional block — возможность docx-драйвера**, presence-driven, all-or-none, membership задаёт required.
  В xlsx родного «блока» нет — вне контракта.
- **repeat не берём** — слои перекрыты отдельными шаблонами на 1–4 слоя (транспонированная таблица = повтор
  колонок, не поддерживается).
- docx-драйвер = text + image + optional block; xlsx-драйвер = text.
- Существующий Proposals-xlsx (label-matching) не трогаем.
- **Картинки — размер (вариант A):** движок только клампит ширину до дефолта (~600px), если не задана; тяжёлую
  обработку/пересжатие не тащит. Лимит веса/разрешения — на аплоаде у потребителя (Symfony `Image`).
- **Опциональность — явная, в шаблоне:** `{{x?}}` — опциональный плейсхолдер, `{{x}}` — обязательный.
  Интроспекция `variables()` возвращает список с флагом `optional`. Опц. отсутствует → `skipped` (не блокирует).
- **Картинки не хардкодятся best-effort** — опциональны, только если помечены `?` (в отчёте — да, поэтому фото не
  стопят генерацию). Два инструмента: `{{x?}}` = пусто на месте; `{{opt_x}}…{{/opt_x}}` = убрать регион целиком.

## 12. Будущее: Деплой 2 (B — управление шаблонами)

Не проектируем сейчас. Гарантия шва: движок Деплоя 1 принимает готовый файл и хранением не занимается, поэтому B
встанет **дополнительным слоем**, а не переписыванием.

Когда B понадобится: шаблоны становятся управляемыми объектами (админ загружает/заменяет файл, система хранит во
Flysystem, список, привязка к фиче, версии). Это состояние + жизненный цикл + инварианты + персистентность +
админка + access-control → **агрегат** `Template{id, name, storageKey, format, …}` в своём bounded context
(новый `Templating` или внутри `Documents` — решим тогда), с репозиторием, use-case «загрузить/заменить/список»,
контроллером и access-control.

Флоу B «сгенерить по шаблону X»: репозиторий поднимает `Template` → берёт `storageKey` → материализует файл из
Flysystem во временный путь → отдаёт путь + `RenderData` фасаду Деплоя 1 → получает `RenderedDocument`. Движок
по-прежнему ничего не знает про хранилище и сущности.

Прецедент формы B в репо: `Proposals\...\ProposalDocumentTemplate` (`id`, `description`, `path`,
`availableFormats`) + репозиторий + ORM-маппинг — то же самое, заточенное под КП.

## 13. Соглашения

- Имена переменных в шаблонах — латиница `snake_case`.
- Значения текста — уже отформатированные строки (даты/числа готовит вызывающий).
- Оформление текста — в самом шаблоне (стилизуй `{{placeholder}}`).
- Опциональное поле — метить `{{x?}}` (нет данных → пусто на месте, не блокирует). Фото метить `?`, чтобы их
  отсутствие не останавливало генерацию.
- Опциональный регион (исчезает целиком) — оборачивай в `{{opt_x}} … {{/opt_x}}` (docx); нет данных внутри →
  регион удаляется. `?` = пусто на месте; блок = убрать регион.
- Слои — отдельные шаблоны на 1 / 2 / 3 / 4 слоя, поля плоские (`{{lN_…}}`).
- Картинки — `ImageValue` с путём; размер опционально (px). Без размера — кламп ширины до ~600px. Лимит веса
  картинок — на загрузке у потребителя (Symfony `Image`: `maxSize`/`maxWidth`/`maxHeight`), не в движке.
