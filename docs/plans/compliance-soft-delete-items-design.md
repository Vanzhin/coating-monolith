# Soft-delete позиций требования Compliance — дизайн

**Дата:** 2026-10-19

**Goal:** Удаление позиции из требования СИЗ делать МЯГКИМ (всегда): позиция остаётся в требовании с флагом `removed`, не выпадает из jsonb. Норм-контроль идёт по активным позициям; название/тип/норма/основание и списание удержанного (held) — по всем позициям (включая удалённые). Это чинит: (а) печать/история теряют название удалённой-но-выданной позиции (сырой ключ вместо имени); (б) held удалённой инвентарной позиции сейчас НЕ попадает в списание (регресс eligible после периодического деплоя).

**Контекст/проблема.** Норма требования меняется редко, но меняется: позицию убирают. Факт выдачи ссылается на `obligationKey = requirementId|itemId` и резолвит название/тип/норму ВЖИВУЮ из позиции нормы по itemId. Жёсткое удаление позиции из jsonb рвёт резолв:
- `obligationLabelOf` → `obligationSpecOf(...)[0] ?? $key` возвращает сырой ключ → в карточке/истории печатается `01a10a82-...|01a1554d-...` вместо названия;
- `writeOffEligibleFactsForRequirement` скоупит eligible по `inventoryKeys` = позиции ТЕКУЩЕЙ нормы (Material) ∪ персональные; удалённой позиции там нет → её held-факт отфильтровывается → **списать нельзя**, хотя по дизайну («списание по held, не по норме») надо.

Дизайн журнальной модели прямо это предвидел («контроль по текущей норме, списание по held; позиция убрана из нормы → не контролируется, но держится и списывается»; «writeOffApplicable — снимок на факте, т.к. норма позиции может уже не существовать»). Выбранная реализация этого — НЕ снимок на факте, а **soft-delete позиции** (сохраняет весь контекст: имя, норму-количество, основание, тип — не только label).

**Решение (approach):** всегда soft-delete. Позиция требования получает флаг `removed`. Сохранение формы мержит (не заменяет): пришедшие позиции остаются/обновляются, отсутствующие существующие по id — помечаются `removed`, новые — добавляются. Потребители делятся на «по активным» (норм-контроль) и «по всем, включая removed» (резолв + списание held).

## Модель (Domain)

**`AbstractRequirementItem` (+ `RequirementItemInterface`)** — добавить `removed: bool` (дефолт false).
- VO `final readonly`: «удаление» = `withRemoved(): static` (возвращает копию с `removed=true`); при необходимости `isRemoved(): bool`.
- `baseArray()`/`jsonSerialize()` пишут `removed` (только если true — чтобы не раздувать jsonb и не ломать round-trip старых; либо всегда — решить в плане, round-trip-тест обязателен).
- `fromArray()` читает `removed` (дефолт false — back-compat).
- `RequirementItemsType` (DBAL) round-trip сохраняет `removed` (пер-айтемно, рядом с `type`).

**`Requirement`:**
- `getItems(): RequirementItemInterface[]` — ВСЕ позиции (вкл. removed). Семантика «все» — для резолва/персиста. (Переименовать в `allItems()` ИЛИ оставить `getItems()`=все + добавить `activeItems()` — решить в плане; важно, что ТЕКУЩИЕ 8 call-sites явно классифицированы ниже.)
- `activeItems(): RequirementItemInterface[]` — только не-removed. Норм-контроль.
- Сохранение состава (новый метод вместо `replaceItems`-replace, напр. `mergeItems(...$submitted)` или доработанный `replaceItems`): по id — обновить присланные; существующие, не пришедшие → `withRemoved()`; новые → добавить. Дедуп по названию — среди АКТИВНЫХ (removed не блокирует новую активную позицию с тем же именем). `supports()`/`accepted()` остаются (тип позиции по `allowsMixedItems`), применяются к добавляемым/активным.

## Развод потребителей (точная карта 8 call-sites `getItems()` + save)

**По АКТИВНЫМ (`activeItems()`):**
1. `RequirementDTOTransformer:29` — форма требования показывает только активные (удалённые скрыты; «удалить» строку = флаг в хранилище).
2. `RequirementCardProjector:94` (`normItems`, стр.1 «норма») — норма карточки = активные (положено сейчас). Удалённые видны лишь в факт-логе стр.2 по резолву.
3. `ComplianceObligationProjector:136` (норм-строки проекции) — активные обязанности (дашборд/`/issue`-предложение, статус-светофор). Removed не краснят и не предлагаются к выдаче.

**По ВСЕМ (`getItems()`=все):**
4. `RequirementCardProjector:125` (`basisByLabel` для факт-строк стр.2) — основание резолвим и для removed (у их фактов основание должно печататься).
5. `ProfileCompliance:187` (`obligationSpecOf` — label/type/cadence/quantity) — резолв по всем, чтобы held-факты removed-позиции звались по-человечески и несли тип/норму.
6. `ProfileCompliance:159` (`inventoryKeys` — eligible списания) — по всем Material (вкл. removed) → held удалённого инвентаря остаётся списываемым. **Чинит регресс eligible.**

**Проекция — отдельно (ключевое):** `ComplianceObligationProjector` строит норм-строки из активных (п.3), НО обязан дополнительно удержать строки removed-позиций, у которых есть held>0 — как НЕактивные (`active=false`/не-контролируемые), чтобы:
- held удалённого инвентаря оставался на экране списания (`/issue` «Списать» / ShowAction читают проекцию/held);
- дашборд их не считал в светофоре (не краснит).
Механика: после активных норм-строк пройти факты требования (`recordsForRequirement`), и для ключей, которых нет среди активных, но held>0 и позиция резолвится как Material (по всем items) — завести строку проекции с `active=false`. (Детали — в плане; согласовать с тем, как проекция сейчас метит `active`.)

**Save:** `SaveRequirementCommandHandler:69` + `Requirement` — мерж вместо replace (см. Модель). Билдер (`RequirementItemBuilder`) не меняется по сути (строит присланные), мерж — на агрегате.

## Миграция данных

`compliance_requirement.items` jsonb — проставить `removed:false` всем существующим позициям (идемпотентно; где `removed` уже есть — не трогать). Данные не теряются. Номер — следующий свободный после `Version20261106122000`. `down()` no-op.

Уже ЖЁСТКО удалённые ранее позиции (из тестов, напр. `01a1554d`) soft-delete не воскрешает — их нет в jsonb. На чистых прод-данных вперёд проблемы нет. Разовый бэкфилл-надгробие (реконструкция из снимка строки списания `label_snapshot`) — ВНЕ scope (при желании отдельной задачей).

## Что чинится

- Карточка/история показывают название удалённой-но-выданной позиции (резолв по всем items), не сырой ключ.
- held удалённой инвентарной позиции снова списывается (`inventoryKeys` по всем Material) — регресс после периодического деплоя закрыт.
- Норма/основание/тип удалённой позиции сохранены (позиция в jsonb, просто `removed`).

## Рулинги (подтверждены с пользователем 2026-10-19)

1. Карточка стр.1 «норма» — только активные; удалённые — лишь в факт-логе стр.2 по резолву.
2. Форма требования показывает только активные; «удалить» = флаг + скрыть; возврат удалённых не делаем сейчас.
3. Уже жёстко удалённые позиции из прошлых тестов не воскрешаем (тест-грязь); на чистых данных вперёд — ок.
4. Миграция проставляет `removed:false`, данные не теряем.
5. Удаление — ВСЕГДА soft (не только для выданных).

## Вне scope

- Снимок label/type на факте (альтернатива, отвергнута в пользу soft-delete).
- UI возврата удалённых позиций.
- Бэкфилл-надгробия для уже жёстко удалённых позиций.
- Блокировка удаления при held>0 (отвергнуто — удаление всегда soft, held списывается по снимку нормы).

## Review focus (что проверить тестами — пограничное)

- Удалить выданную позицию → карточка/история показывают её НАЗВАНИЕ (не ключ); held остаётся; позиция списывается актом; дашборд её не краснит.
- Удалить НЕвыданную позицию → тоже soft (в jsonb `removed`, из активных ушла), резолв работает.
- Round-trip формы: сохранить → убрать позицию → сохранить → позиция `removed`, прочие целы; вернуть ту же по названию активной — дедуп не падает.
- Проекция: removed+held>0 → строка есть (для списания), active=false (не в светофоре); removed+held=0 → не мешает.
- Миграция round-trip: старый jsonb без `removed` → читается (дефолт false) → пишется с `removed`.
- `inventoryKeys`: removed Material с held → eligible; removed Periodic → НЕ eligible.

## Открытые вопросы (решить в плане)

- `getItems()` оставить = «все» + добавить `activeItems()`, или переименовать. Выбрать так, чтобы 8 call-sites читались однозначно.
- Как именно проекция метит `active` для removed+held строк (согласовать с текущим `ObligationProjection.active`).
- `removed` в jsonb писать всегда или только при true (round-trip + размер).
