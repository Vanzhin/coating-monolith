# Inquiries, план 12: кэш точного дубликата (хеш входа → копия параметров, без модели)

Дата: 2026-10-29. Безопасный «точный хеш»-тир кэша: запрос с таким же ВХОДОМ переиспользует уже распознанные параметры близнеца, модель не зовём. Помогает пачкам одинаковых писем и повторным присылкам (план 10) и вебу. НЕ путать с семантическим кэшем/примерами (план 8, эмбеддинги, запаркован до накопления). См. [[project_inquiries_accuracy_and_mail]].

## Зачем

Пришла пачка писем с одинаковым текстом+вложениями (дублированная доставка, пересылка) → каждое заводит свой запрос (свой владелец/уведомление, план 10), но распознавать 10 раз одно и то же — трата токенов/времени. Одинаковые байты → гарантированно тот же ответ (без риска схлопнуть «нефть 80»/«нефть 90» — это ТОЧНОЕ совпадение, не похожесть). Это и есть «снять копию» параметров.

## Опора (крючок уже есть)

- `SystemSelectionProcessor` ПЕРЕД вызовом модели зовёт `cache->lookup(type, assembledText)`; на попадании берёт параметры близнеца с `ParameterStrategy::Cache` и источником — модель НЕ зовёт. Сейчас `ApprovedParameterCache` = `NoopApprovedParameterCache` (всегда промах). Наполняем его по хешу.
- `CacheHit{parameters: RecognizedParameters, sourceInquiryId}` — готовый контракт.
- Ключ — **собранный текст** (`assembler->assemble()`: тело+вложения с метками, уже считается в процессоре). Это ИМЕННО вход распознавания → хеш от него = правильный ключ «тот же вход → тот же выход». Детерминирован (тело + механически извлечённый текст вложений стабильны для того же письма).

## Решения

- **Хеш от собранного текста** (нормализуем: трим + схлопывание пробелов → sha256). Единый ключ для веба и почты.
- **content_hash — инфраструктура**, не доменное поле (техника кэша/поиска, как FTS-tsvector в Coatings): колонка на таблице inquiry, ведётся при обработке, агрегат о ней не знает.
- **Кэш ищет среди Recognized И Approved** (не только Approved!) — иначе пачка, пришедшая до первого одобрения, не переиспользуется. Распознал первый → остальные в пачке снимают копию.
- **Копия = переиспычиваем РАСПОЗНАННЫЕ ПАРАМЕТРЫ**, не подобранные системы. Систем не храним (живой прогон), параметры стабильны для того же текста — устаревания нет (в отличие от старого answer-snapshot).
- Гонка пачки (одинаковые пришли разом, близнец ещё `Received`) → ждём ведущего (см. раздел ниже), а не зовём модель каждым. `Failed`-близнец не переиспычиваем.

## Гонка пачки: ожидание ведущего

Пачка из N одинаковых создаётся разом → N заданий в очереди. Чтобы модель вызвалась ОДИН раз (а не N при параллельных воркерах), дубликаты ждут ведущего и копируют.

Логика обработки запроса B:
1. Есть РАСПОЗНАННЫЙ близнец (Recognized/Approved, тот же хеш/тип) → **копируем параметры** (Cache, sourceInquiryId), готово.
2. Есть одинаковый в обработке с МЕНЬШИМ id (раньше) и `waitAttempt < N` → **отложенный requeue +60с** (`waitAttempt++`), выходим (модель не зовём).
3. Иначе (B — ведущий / выждали кап) → обычный путь к модели.

Страховки:
- **Ведущий = наименьший ULID** среди одинаковых по хешу. B ждёт только при наличии одинакового с МЕНЬШИМ id. У кого id минимальный — ведущий, зовёт модель; остальные видят более раннего и ждут именно его. ULID монотонный+уникальный → ровно один ведущий, без дедлока «все ждут всех».
- **Кап ожидания N** (напр. 3×60с): ведущий упал/завис → ждущие после N попыток сдаются и обрабатывают сами. Без вечного ожидания.

Механизм: messenger `DelayStamp(60с)` на переотправке `ProcessInquiry`, счётчик `waitAttempt` на сообщении. `Failed`-близнец ведущим не считаем (его параметров нет).

## Что меняется

- **Миграция:** колонка `inquiry.content_hash` (nullable, индекс). Идемпотентно.
- **content_hash пишется при обработке** из собранного текста (нормализ.+sha256). Держим вне агрегата (инфра-запись после recognize — по образцу FTS-проектора; не класть на доменный `Inquiry`). Процессор уже держит собранный текст — он даёт хеш.
- **Реальный `ApprovedParameterCache` (хеш-бэкенд)** взамен Noop:
  - `lookup(type, text)` → нормализ.+хеш → репозиторный резолв «последний Recognized/Approved запрос этого типа с таким content_hash» → `CacheHit(его параметры, его id)` или null.
  - `index(inquiry)` → гарантирует, что content_hash запроса сохранён (или no-op, если пишем при обработке).
- **Репозиторий:** узкие методы резолва (не пользовательский поиск — отдельные методы, как `findOneById`; НЕ ось в `InquiriesFilter`): `findRecognizedByContentHash(hash, type): ?Inquiry` (копия параметров) и `findEarlierInflightByContentHash(hash, type, beforeId): ?Inquiry` (есть ли ведущий раньше B).
- **`ProcessInquiry`-сообщение + хендлер** — `waitAttempt` на сообщении; при «ждём ведущего» переотправка с `DelayStamp(60с)` и `waitAttempt++` вместо обработки.
- `ParameterSource` на копии — `Cache` + `sourceInquiryId` (провенанс уже поддержан, origin значений в `RecognizedParameters` станет `Cache`).

## Развилки (решены / к решению)

- Ключ — собранный текст, не сырой email. (решено: это настоящий вход распознавания, единый для веба/почты)
- Искать среди Recognized+Approved. (решено)
- Копируем параметры, не ответ. (решено)
- Нормализация текста перед хешем — трим+пробелы; агрессивнее (срезать подписи/цитаты) — не сейчас (риск коллизий), только если дубли будут проскакивать.

## Не входит

- Семантический кэш/похожесть на эмбеддингах + динамич.примеры — план 8 (запаркован).
- Инвалидция по изменению справочника — не нужна (кэшируем ПАРАМЕТРЫ, они от текста, не от каталога).

## Тесты

- `ApprovedParameterCache` (functional, нужна БД): два запроса с одинаковым собранным текстом — второй `lookup` возвращает параметры первого (Recognized); разный текст — промах; `Failed`-близнец не отдаётся; разный тип — промах.
- `SystemSelectionProcessor` (unit): на попадании кэша модель НЕ зовётся, origin `Cache`, source выставлен (кейс уже частично есть — `test_cache_hit_skips_model`).
- Хеш (unit): нормализация (пробелы/трим) → один хеш; разный текст → разный.
- Пачка (functional, опц.): N одинаковых → 1 распознан моделью, остальные Cache.
- Ожидание ведущего (unit на решение): близнец `Received` с меньшим id + attempt<N → requeue с задержкой (модель не зовётся); B с наименьшим id → обрабатывает; attempt≥N → обрабатывает сам (ведущий завис).

## Порядок (один деплой; после плана 11; независим от плана 10)

1. Миграция content_hash + запись хеша при обработке (инфра).
2. Хеш-реализация `ApprovedParameterCache` + репо-метод резолва.
3. Тесты (functional кэш + unit процессор/хеш).
4. Гейты, прогон: отправить дубль — второй снимает копию без вызова модели (видно по `ParameterSource` = Cache и отсутствию аудит-записи исходящего к NetAngels).
