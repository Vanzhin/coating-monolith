# Inquiries, план 8: динамические примеры из одобренных (few-shot на эмбеддингах)

Дата: 2026-10-29. Шаг 2 роадмапа `inquiries-accuracy-roadmap.md` — главный рычаг точности. Опирается на план 7 (`inquiries-7-eval-set.md`: робот+человек в оси + градусник) и на его же эталон для проверки эффекта. **Гейт инфраструктуры:** нужна эмбеддинг-модель (сайдкар/эндпоинт) — без неё план не стартует (см. ниже).

## Зачем

Сейчас модель решает «с нуля» по статичным правилам промпта. Правила — слабый способ учить: каждый частный случай — новая строка, промпт пухнет, а модель всё равно трактует по-своему. Сильнее — показывать **примеры решений**: перед вызовом подкладываем 2–3 наиболее похожих одобренных запроса («вот текст — вот параметры, которые в итоге одобрил инженер»). Модель подстраивается под практику, включая неписаные правила.

Даёт и точность, и одинаковость: похожие входы тянутся к одним примерам → к одним ответам. **Безопаснее кеша (план 5):** модель читает реальный текст этого запроса, «нефть при 80» и «нефть при 90» не схлопываются; промах ретривера не страшен — это лишь подсказка, а не молчаливый ответ.

## Решения, принятые на обсуждении

- **Примеры УЧАТ модель, не заменяют её.** Модель всё равно запускается и читает текущий текст. Замена-модели-кешем — это план 5, отдельно и последним.
- **Без отдельной таблицы.** Пул примеров — это сами одобренные запросы. Эмбеддинг — КОЛОНКА на таблице `inquiry` (не новая таблица). Поиск ближайших — `ORDER BY embedding <=> :vec`.
- **Эмбеддинг — обращение к модели (text → вектор), сравнение векторов — код/БД (pgvector).** Модель эмбеддинга — предпочтительно локальный CPU-сайдкар (приватность писем + нулевая стоимость вызова + повторяемость); пока его нет — за портом.
- **Эмбеддинг — инфраструктура** (техника поиска), не доменное поле. Колонку ведёт проектор (как tsvector-FTS в Coatings), пишет её по DBAL после одобрения, НЕ через агрегат.

## Гейт: эмбеддинг-модель

План не начинаем, пока нет способа считать эмбеддинг. Ресурсы скромные (e5-small ~0.5 ГБ диск / ~1 ГБ RAM, CPU, без GPU; объём запросов копеечный). Варианты: локальный сайдкар (HF text-embeddings-inference, OpenAI-совместимый HTTP) или готовый эндпоинт. Проверить у NetAngels наличие эмбеддинг-эндпоинта; если нет — поднять сайдкар. До этого порт `TextEmbedder` живёт с заглушкой, остальной код плана ждёт.

## Что меняется

1. **Миграция (НЕ новая таблица):** расширение `pgvector`; колонка `text_embedding vector(N)` на `inquiry` (N по модели, напр. 384). Идемпотентно (`CREATE EXTENSION IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`). + ivfflat/hnsw индекс по колонке.
2. **Порт `TextEmbedder`** (Shared или Inquiries/Application/Port): `embed(string $text): array` (вектор). Реализация — HTTP к сайдкару/эндпоинту за общим http-client (с аудитом, как извлечение). Заглушка до гейта.
3. **Проектор эмбеддинга** (Infrastructure): на одобрении считает эмбеддинг собранного текста (ассемблер) и пишет в колонку `inquiry.text_embedding` по DBAL. Триггер — там же, где `ApproveInquiryCommandHandler` уже зовёт `cache->index($inquiry)` (хук есть). Домен про колонку не знает.
4. **Порт `ApprovedExamplesProvider`**: `findSimilar(InquiryType $type, string $text, int $k): ApprovedExample[]` — эмбеддит запрос, тянет k ближайших одобренных того же типа (`WHERE status='approved' AND type=:t AND id <> :self ORDER BY text_embedding <=> :vec LIMIT :k`). `ApprovedExample` = DTO {текст, `RecognizedParameters`} из найденного запроса.
5. **Составной промпт:** `SystemPromptBuilder` → постоянная часть (правила/схема, v3) + блок few-shot примеров. `InquiryParametersExtractor::extract` принимает примеры (или их принимает сборщик запроса к модели). В `ParameterSource.details` — id показанных примеров (для разбора: какой сосед увёл).

## Развилки (решить при реализации)

- **K примеров** — старт 2–3 (токен-бюджет; промпт v3 уже ~14 КБ).
- **Большие письма-примеры дорогие** — класть в few-shot не весь текст примера, а короткий гист + его параметры (параметры компактны). Калибровать.
- **Порог близости** — брать top-K без порога (всегда k ближайших) или отсекать по минимальной близости (если ничего похожего — не подкладывать мусор). Старт: top-K, порог — по наблюдению.
- **Модель эмбеддинга и размерность N** — от доступного сайдкара/эндпоинта.
- **Эталон не должен жульничать (leave-one-out).** Градусник (план 7) при активных примерах обязан НЕ подкладывать запросу его собственный пример (в `findSimilar` уже `id <> :self`), иначе точность завышается. Для оценки эффекта примеров — мерить на отложенной выборке или строго leave-one-out.

## Не входит

- Семантический кеш «тот же вопрос — тот же ответ без модели» (план 5, `inquiries-5-templates-and-cache.md`) — последним, на плато точности; он замораживает ошибки, здесь мы их наоборот исправляем.
- Дообучение модели (роадмап «не делать сейчас»).

## Тесты

- Unit `ApprovedExamplesProvider` с мок-`TextEmbedder` и мок-репозиторием: зовёт embed, прокидывает k, исключает сам запрос.
- Unit сборки промпта: примеры попадают в few-shot блок в нужном формате; без примеров — промпт как v3.
- Unit/functional извлечения: экстрактор прокидывает примеры в запрос к модели.
- Функционально проектор + `findSimilar` — с pgvector в тест-образе (если поднимем) либо отложить до сайдкара.
- Эффект примеров — прогоном градусника (план 7) с leave-one-out до/после.

## Порядок

1. Гейт: поднять эмбеддинг (сайдкар/эндпоинт) + `TextEmbedder` реализация.
2. Миграция: pgvector + колонка + индекс.
3. Проектор эмбеддинга на одобрении.
4. `ApprovedExamplesProvider` + `ApprovedExample`.
5. Составной промпт + проброс примеров в экстрактор.
6. Прогон по градуснику (leave-one-out) — замер прироста точности по осям.
