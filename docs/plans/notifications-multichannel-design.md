# Многоканальные уведомления — дизайн (обзор)

Дизайн-документ (источник правды для деплоев ниже). Цель — единый способ «уведомить
пользователя/группу» через сменные каналы (email, telegram — есть; web push — добавляем; sms и
др. — потом), с чёткими границами ответственности и швом под настраиваемые подписки.

## Что уже есть и НЕ меняется
- **Контракт доставки** — `Shared/Domain/Service/NotifierInterface`:
  `notify(Channel $channel, string $message)`, `sendVerificationCode(Channel, code, ttl)`,
  `isSupportedChannel(Channel): bool`.
- Реализации: `EmailNotifier` (обёртка `Mailer`), `TelegramNotifier` (обёртка `TelegramBotService`).
- `NotifierFactory::create(ChannelType): NotifierInterface` (match по типу), фасад
  `ChannelNotifierService::notify(Channel, message)`.
- `Users\Domain\Entity\Channel` — контакт пользователя: `ChannelType $type`, `string $value`,
  `User $owner`, флаг verified + OTP-верификация. `ChannelType`: EMAIL, TELEGRAM.
- Асинхрон — **Symfony Messenger** + транспорт `async` = Redis (`config/packages/messenger.yaml`).
  Позже RabbitMQ — смена DSN, код не трогает.

Контракт `NotifierInterface` НЕ трогаем (по указанию заказчика). Новый канал = +значение enum,
+класс нотифайера, +строка в фабрике.

## Слои ответственности
1. **Доставка (`Notifier`)** — «дали `(channel, message)` — шлю». Ничего не решает: ни кому, ни
   обязательность, ни подписки. Про push/email/sms знает только конкретный нотифайер за интерфейсом.
2. **Диспетчер = async-обработчик события.** На доменное событие: определяет получателей и их
   каналы → на каждый канал зовёт `ChannelNotifierService.notify(...)`. Фан-аут **по получателям**
   (каждый — своё async-сообщение → параллельно, изолированный ретрай, без масс-дублей); внутри
   одного получателя его 1–3 канала шлём inline, best-effort (try/catch на канал — падение одного
   не роняет остальные и не фейлит сообщение ради дубля).
3. **Получатели («кому + куда»)** — НЕ в доставке, а в слое диспетчера:
   - **Обязательные** уведомления — получатель/канал из доменного правила (владелец сущности,
     роль). Пользователь не управляет.
   - **Настраиваемые** (ограниченный список, opt-in по каналам) — из хранилища подписок. Может,
     не строим сейчас (см. шов).

## Классы уведомлений
- **Обязательные**: напр. «изменение покрытия → владельцу на почту», события «требуют действия».
  Обработчик сам резолвит. (Прим.: у покрытия сейчас НЕТ владельца — это предпосылка конкретного
  триггера, отдельная задача, не часть этой архитектуры.)
- **«Требует действия»** — не отдельная механика, а **содержимое**: сообщение со ссылкой/CTA
  (email со ссылкой, push с url). Отправитель шлёт как есть.

## Шов под настраиваемые подписки (закладываем, НЕ реализуем)
Подписки живут НАД доставкой. Когда понадобятся — добавляем в слой диспетчера:
- хранилище `NotificationSubscription (user, eventKey, channelType)` — «подписан ли юзер X на
  событие E по каналу C»; событие И ЕСТЬ ключ (без отдельного каталога «типов»);
- сервис-резолвер «дай получателей+каналы для события E», который обработчик спрашивает;
- UI в кабинете (тумблеры по событиям/каналам).

Это НЕ трогает `Notifier`, `ChannelNotifierService`, `NotifierFactory` и асинхрон — добавляется
сверху. Поэтому «встроить легко потом» выполняется само собой: пока слоя подписок нет, обработчик
резолвит получателей доменным правилом (обязательные); появится — обработчик спрашивает резолвер.

## Канал Web Push (первый деплой — см. отдельный план)
Одна подписка браузера = один `Channel` типа `WEB_PUSH`, `value` = JSON подписки
(`endpoint`/`p256dh`/`auth`), создаётся сразу `verified` (согласие даёт браузер, OTP не шлём). У
юзера может быть несколько (разные устройства) → фан-аут по устройствам получается сам собой
(каждое — отдельный Channel). `WebPushNotifier`: декодит value, шлёт через `minishlink/web-push`,
мёртвую подписку (ответ 404/410) деактивирует/удаляет. `sendVerificationCode` для WEB_PUSH —
no-op (или тест-пуш). Плюс VAPID, обработчики `push`/`notificationclick` в SW, фронт-подписка.

## Уровень асинхронности (решено)
Фан-аут **по получателям**, каналы внутри получателя — inline best-effort. Пер-канальные
async-сообщения (изоляция/ретрай конкретного канала) — апгрейд нутра диспетчера на будущее
(массовые рассылки/критичная доставка/капризные внешние гейты), контракт не меняет.
