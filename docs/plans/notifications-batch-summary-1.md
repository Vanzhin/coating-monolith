# Уведомления: одно сообщение на получателя (пачка от проходчика, отправки по одной)

Статус: план, ждёт подтверждения. Код не тронут.
Ветка: `feat/notifications-batch-summary`.
Сосед: часть 2 «не повторять неизменное каждый день» — отложена, плана нет. Этот план самодостаточен.

## Принятое направление (важно)

Делаем **batch-at-source**: источник, который знает, что у него пачка (проходчик), публикует её одним событием; слой уведомлений схлопывает по получателю. Это **и есть система**, а не костыль: любой будущий «пачечный» источник просто публикует `NotificationBatch`, механизм схлопывания один и типонезависим. Граница пачки задаётся источником — честнее, чем угадывать таймером конец всплеска.

Сознательно НЕ делаем персистентную outbox-таблицу + flush по таймеру: единственный источник всплесков сейчас — проходчик, остальные события одиночные. Понадобится — добавим отдельно, не ломая этот путь.

Попутно (сложено в этот план по решению пользователя) упрощаем модель каналов: подписных каналов два — **приложение (inbox) и почта**; **push перестаёт быть подписным каналом** и шлётся автоматически при появлении записи в приложении.

## Зачем

Проход сроков (`DueSoonScanner`) публикует событие на каждого сотрудника. Резолвер кладёт администратора в адресаты каждого события: при 100 сотрудниках администратор получает 100 сообщений.

Нужно: **число сообщений равно числу получателей, а не числу событий.** Плюс: текст короткий, со счётчиками и ссылкой на дашборд; сбой одной отправки не трогает остальные каналы.

## Как это работает

```
проходчик ──(1 пачка: все события прохода)──▶ раскладка ──(N отправок)──▶ отправка
                                               │                            │
                              по получателям×тип×перспектива,     одна доставка = одно
                              формирует ТЕКСТ, сам не шлёт        сообщение очереди (inbox|email)
```

1. **Проходчик** создаёт события как сейчас, но копит их и в конце прохода публикует одной пачкой `NotificationBatch`.
2. **Раскладка** раскладывает события по стопкам **(получатель, тип, перспектива)**, по каждой стопке **формирует один текст** (единственное место, где видна вся стопка — значит и сводка возможна только здесь) и публикует отправки: одна отправка — «получателю X по каналу Y такой-то текст». Сама не шлёт и в БД не пишет.
3. **Отправка** берёт одну отправку, доставляет готовый текст (inbox-запись / письмо), подтверждает. На создании inbox-записи — пинг push на устройства получателя.

**Перспектива** — ключевое: для каждой пары (событие, получатель)
- получатель = субъект события (сам сотрудник) → стопка **«про меня»** → персональный текст;
- получатель ≠ субъект (админ) → стопка **«про других»** → сводка.

Админ со своими сроками получает **два** сообщения: персональное (как владелец) и сводку (как админ). Правило одно для всех — спецкейса на админа нет.

Между шагами ничего не хранится, кроме самой очереди Redis: новых таблиц и расписаний нет.

## Ключевые решения

1. **Стопка собирается в памяти из пачки проходчика.** Таблиц-очередей, таймеров, хранения в Redis нет. Пачка ≈ 1,7 КБ/событие (1 000 сотрудников ≈ 1,6 МБ) при лимите PHP 1024 МБ.
2. **Одна доставка — одно сообщение очереди** (получатель × канал). Ошибки — штатный Symfony-ретрай: повтор только упавшей отправки, затем `failed`. Своих `try/catch` нет.
3. **Каналы независимы — это чиним.** Сейчас `NotificationDispatcher` доставляет все каналы в одном обработчике без `try/catch`, а `EmailNotifier::notify` бросает при сбое почты → падает весь обработчик → Symfony повторяет всё событие → дубли inbox/push. Разбивка «одна отправка — один канал» делает ретрай точечным.
4. **Текст формируется в раскладке**, не в обработчике доставки: сводка строится из всей стопки, а стопка есть только в раскладке. Обработчик получает готовую строку. Один текст на все каналы (MVP, `notifications-subscriptions-design.md` п.6).
5. **Одиночное событие идёт тем же путём** — пачка из одного.
6. **Раскладка только читает.** Отправки публикуются через `EventBus` со штампом `DispatchAfterCurrentBusStamp`: раскладка упала → ни одна отправка не ушла (проверено по `DispatchAfterCurrentBusMiddleware`, messenger 8.0.15).
7. **Перспектива определяется раскладкой** по субъекту: для `SubjectNotification` владелец берётся через существующий порт `SubjectContextProviderInterface::userUlidOfProfile`; получатель == владелец → «про меня», иначе → «про других». Событие без субъекта → все «про меня». Резолверы и события по контракту НЕ меняем.
8. **Рассылка — только `Soon` и `Overdue`.** `Missing` в эту итерацию не входит (самый объёмный бакет; без части 2 слал бы «не выдано» всем ежедневно). Позже, вместе с дедупом.
9. **Получатели due — владелец + админы.** Начальник отдела — отдельная задача (нужен ещё доступ к подчинённым на дашборде).
10. **Ссылку строит `UrlGenerator` (ABSOLUTE_URL), без своего порта/абстракции.** В коде — только имя маршрута `app_cabinet_compliance_dashboard` + параметры; хост Symfony подставляет из `router.default_uri`. Домен нигде в коде не пишем — он в конфиге (env), задаётся на деплое.
11. **Каналы: подписные — приложение (inbox) и почта.** `push` убираем из подписных каналов; шлётся автоматически при создании inbox-записи (пинг «есть новое в приложении»). Это разворачивает расцепление авто-push из Phase 1 — осознанно. Устройства/эндпоинты web-push (из multichannel) остаются целями пинга.
12. **Тип без сводочного текста** шлёт события по одному. Название типа `ComplianceDueSoon` оставляем («СИЗ: подходит срок выдачи»).

## Тексты (нужно подтверждение формулировок)

Про меня (персональный):
```
Иванов Иван Иванович — срок подходит у позиций: 3, просрочено: 1.
<абсолютная ссылка>/cabinet/compliance/dashboard?profile=<id>
```

Про других (сводка):
```
Сотрудников: 5 — срок подходит у позиций: 15, просрочено: 7.
<абсолютная ссылка>/cabinet/compliance/dashboard?only=1
```

Правила: нулевой счётчик не выводится; «Сотрудников» — число событий в стопке «про других»; остальные — число позиций в состоянии по всем событиям стопки; Missing не участвует.

## Ссылка на дашборд

Маршрут `app_cabinet_compliance_dashboard`; `IndexAction` читает `profile=<id>`, `status=<bucket>`, `only=1` (проверено). Рендерер строит ссылку через `UrlGeneratorInterface::generate(..., ABSOLUTE_URL)`.

| Сообщение | Параметры |
|---|---|
| про меня | `profile=<id>` |
| сводка, только «подходит срок» | `status=soon` |
| сводка, только «просрочено» | `status=overdue` |
| сводка, «подходит срок» + «просрочено» | без фильтра состояния (отдельного фильтра «soon+overdue» у дашборда нет) |

**Где кликабельно.** В письме и разделе «Уведомления» — да (T6). В push клик ведёт в раздел уведомлений (`sw.js.twig`), там ссылка кликабельна.

**Базовый адрес (хост).** Тексты рендерятся в воркере, вне HTTP → хост берётся из `router.default_uri`. Сейчас он задан только для dev и равен `http://localhost:6878` (порт по compose — 8080), для prod не задан. Правим: `default_uri: '%env(APP_BASE_URL)%'` для всех окружений; `APP_BASE_URL` — dev `http://localhost:8080`, prod — адрес сайта (значение задаёт деплой, в коде не пишем).

## Что НЕ входит

- `Missing` в рассылку (реш. 8); начальник отдела как получатель + его доступ к дашборду (реш. 9).
- Часть 2 (не повторять неизменное): пока одно сообщение в день, но каждый день.
- Разный текст по каналам.
- Персистентная outbox/таймер/коалесинг независимых всплесков.
- Блокировка расписания от двойного прохода; уникальное имя Redis-потребителя для нескольких воркеров.
- Новые фильтры дашборда. Миграций БД нет.

## Что будет при сбое

| Сбой | Поведение |
|---|---|
| Ошибка раскладки | ни одной отправки; 3 повтора пачки (1/2/4 с), затем `failed`; `messenger:failed:retry` безопасен |
| Ошибка одной отправки (почта) | 3 повтора только её, затем `failed`; остальные каналы/получатели не затронуты |
| Сбой пинга push | залогирован, inbox-запись не откатывается и не повторяется (push best-effort) |
| Воркер погиб посреди отправки | после рестарта берёт неподтверждённое; подтверждённые не повторяются |
| Redis недоступен при публикации отправок | пачка повторяется; успевшие отправки продублируются (окно — мс) |

## Review Focus

- Одиночные события сохраняют поведение: `NotificationDispatcherTest`, `UserActivatedEventHandlerTest` зелёные без правок (держится на `sync` в `when@test` — проверить на T3).
- Админ со своими сроками → два сообщения (персональное + сводка).
- Получатель без каналов → ни одной отправки.
- **Независимость каналов** (реш. 3): сбой почты не трогает inbox и не плодит дубли.
- **Push как пинг на inbox**: создаётся запись → пинг на устройства; сбой пинга не ломает inbox; push убран из подписок, но web-push-устройства всё ещё пингуются.
- Фильтр `notification_text`: экранирование до оживления ссылок; чужой адрес остаётся текстом.
- Раскладка не пишет в БД и ничего не шлёт.
