# Inquiries, план 10: почтовый адаптер (IMAP → запрос на подбор)

Дата: 2026-10-29. Приём запросов с почты: адаптер слушает выделенный ящик и превращает письма в запросы через СУЩЕСТВУЮЩИЙ конвейер. Парная задача — `inquiries-11-processed-event.md` (уведомление «обработан»). См. [[project_inquiries_accuracy_and_mail]].

## Решения (зафиксированы)

- **Транспорт — IMAP-опрос** выделенного ящика. Scheduler дёргает периодически (~2-5 мин), тянет непрочитанные, помечает `\Seen`. Библиотека — `webklex/php-imap` (чистый PHP, без ext-imap в образе).
- **Выделенный ящик — всякое письмо = кандидат в запрос.**
- **Отправитель → пользователь.** Резолвим email отправителя в пользователя (`UserRepositoryInterface::getByEmail` уже есть, но зовём через Users Application-query — кросс-контекст).
  - **Найден** → заводим запрос, владелец = этот пользователь.
  - **НЕ найден** → запрос НЕ заводим, **ответом НЕ отвечаем** — просто скип (решено: не пользователь = не наша работа, молча выходим). Письмо помечаем `\Seen`.
- **Дедуп** — флаг `\Seen` (обработанное не перечитывается). Таблица Message-ID — при необходимости позже.
- `raw_text` запроса = тема + тело письма. Вложения → общая `StageFilesCommand` (её guard: allow-list mime pdf/docx/xlsx/картинки + лимит 15 МБ уже есть), недопустимое вложение скипаем именно его (лог), письмо обрабатываем дальше.

## Флоу

Scheduler → `app:inquiry:poll-mail` → `ImapMailboxReader` тянет непрочитанные → для каждого письма:
1. Резолв email отправителя → пользователь (через Users-query, в ingest-хендлере Inquiries).
2. **Нет пользователя:** `skipped` — ничего не заводим и НЕ отвечаем, `\Seen`, дальше.
3. **Есть:** собрать текст (тема+тело), застейджить вложения, `CreateInquiryCommand(type, rawText, fileIds, ownerId = userId)` → дальше конвейер БЕЗ изменений (Received → InquirySubmitted async → воркер распознаёт → градусник → событие «обработан», план 11). `\Seen`.

Адаптер тонкий: распознавание/дедуп параметров/дашборд не трогаем.

## Что меняется

- **Зависимость:** `webklex/php-imap`.
- **Порт+реализация `InquiryMailReader`** (Infrastructure) — тянет непрочитанные, отдаёт нормализованные письма `{messageId, fromEmail, subject, textBody, attachments: list<{name, bytes/mime}>}`, помечает `\Seen`. Механизм IMAP целиком внутри.
- **Команда-поллер `app:inquiry:poll-mail`** (Console, под Scheduler) — оркестрация флоу выше. Актор — система (`ConsoleAuthenticationSubscriber` → `SystemUser`, проходит capability-гейт `CreateInquiry`).
- **Расширить `CreateInquiryCommand`** опциональным `?string $ownerId`. Хендлер: `owner = $command->ownerId ?? $this->access->currentUserId()` — переданный владелец (почта) в приоритете, иначе текущий актор (веб/консоль). Гейт `canManage()` на месте. Нужно, т.к. поллер бежит системой (`currentUserId()='system'`), а владелец — резолвнутый отправитель; поэтому переданный приоритетнее, иначе система затёрла бы его.
- **Users: query `GetUserIdByEmail`** (Application, через шину) → `?string` (обёртка над `getByEmail`), чтобы Inquiries не лез в чужой репозиторий напрямую.
- **Ingest-хендлер `IngestInquiryEmail`** (Inquiries Application) — единственная забота: гейт `canManage` + резолв отправителя через `GetUserIdByEmail`; нашёл → делегирует `CreateInquiryCommand` с `ownerId`; не нашёл → `skipped` (ответа нет). Проверка прав — ТОЛЬКО тут, в accessControl, не по каждому отправителю.
- **Конфиг:** IMAP host/port/encryption/user/pass/folder в `.env` (`INQUIRY_IMAP_*`). Документировать в `.env.example` (ПУСТО для user/pass, чтобы CI не падал, как с mailer/telegram — см. [[reference_ci_test_mailer_dsn]]; пустой user → `ImapAccount::isConfigured()=false` → поллер молча выходит).
- **Регистрация в Scheduler** — рядом с проходчиком уведомлений (06:00) [[project_notifications_subscriptions]], но по интервалу.

## Устойчивость

- Кривое/пустое/оверсайз письмо, сбой стейджа одного вложения, сбой резолва — **скип+лог, поллер не падает**, остальные письма пачки обрабатываются. Непомеченное `\Seen` при падении переобработается в следующий проход (идемпотентность CreateInquiry по телу не гарантируется — поэтому `\Seen` ставим ТОЛЬКО после успешной обработки письма).

## Развилки (решены / дефолты)

- IMAP-либа — `webklex/php-imap` (без ext-imap). (решено)
- Дедуп — `\Seen`, Message-ID-таблица позже. (решено)
- Нет юзера → молча скип, запрос не заводим, ответа нет. (решено)
- Интервал Scheduler — старт 5 мин, подстроим.
- `raw_text` = тема+тело. (решено)

## Не входит

- Любой ответ отправителю по почте (и «не пользователь», и результат подбора) — не здесь, молча скип.
- Threading/привязка ответов к существующему запросу — каждое письмо = новый запрос.
- Уведомление «обработан» — план 11.
- **Переиспользование параметров для одинаковых по СОДЕРЖАНИЮ писем** (не того же IMAP-сообщения — его ловит `\Seen`). Каждое письмо заводит СВОЙ запрос (свой владелец/уведомление); если содержимое совпало с уже распознанным — параметры копируются через кэш по хешу, модель не зовётся. Это `inquiries-12-exact-hash-cache.md`, не здесь. Поэтому content_hash в плане 10 НЕ считаем — он живёт в плане 12 (хеш от собранного текста при обработке, единый ключ для веба и почты).

## Тесты

- `InquiryMailReader` — на фикстурах `.eml`/моке: парс from/subject/body/attachments, пометка `\Seen`.
- Поллер — мок reader: найден юзер → `IngestInquiryEmailCommand` → `created`, `\Seen` поставлен; не найден → `skipped`, ответа нет; сбой одного письма не рушит пачку и НЕ ставит `\Seen` (переиграется).
- `GetUserIdByEmail` — найден/не найден.
- `CreateInquiryCommandHandler` (functional) — переданный `ownerId` применяется (приоритетнее актора); без `ownerId` — владелец = актор.

## Порядок (один деплой)

1. `GetUserIdByEmail` + расширение `CreateInquiryCommand`/хендлера (`ownerId`) + тесты.
2. `webklex/php-imap` + `WebklexMailboxReader` (порт `MailboxReader`) + конфиг + тесты.
3. `IngestInquiryEmailCommand`/хендлер (гейт + резолв + делегирование) + тесты.
4. Поллер-сервис + консоль `app:inquiry:poll-mail` + Scheduler + устойчивость + тесты.
5. Гейты, прогон на тестовом ящике.
